## Фикстуры

- **Реальные игры в репозиторий не коммитим никогда.** Фикстуры генерирует код в `yaoplm-test-support` (свой генератор ISO9660, ADR-0016; готовые варианты `SYSTEM.CNF` — `Variant`):
  - крошечный ISO9660 с `SYSTEM.CNF` (`BOOT2 = cdrom0:\SLUS_200.62;1`) и пустым ELF;
  - варианты без `BOOT2`, с другим регистром, с длинным ID;
  - BIN/CUE (сырые 2352-байтные секторы) из того же ISO;
  - ZSO из того же ISO;
  - мини-DAT в формате Logiqx;
  - образ FAT32 на несколько МБ (`FatImage`, через `fatfs`);
  - `VirtualFile`/`VirtualIso`: поток на 4,5 ГиБ, генерируемый на лету, для тестов нарезки; `VirtualSources` подставляет такие файлы как источники импорта;
  - `MemFs`: устройство в памяти с семантикой FAT (имена без учёта регистра, лимит 4 ГиБ − 1, свободное место), большие файлы хранятся «пробами» по 16 байт через каждый МиБ, `unplug_after(n)` имитирует выдернутую флешку, `fail_once` — сбой одной операции;
  - `bincue`: BIN/CUE во всех четырёх режимах секторов (MODE1/2048, MODE1/2352, MODE2/2336, MODE2/2352), с паузой перед дорожкой и без.
- Эталоны (golden) лежат в репозитории как маленькие бинарные файлы. В `.gitattributes` они помечены `binary`, чтобы CRLF в CFG не портился.

## Перекрёстные проверки

- **ZSO:** `ziso.py` из репозитория OPL распаковывает наши файлы (`align` 0 и 2), а мы читаем его файлы (`-c 1` и `-c 9`). Тест `crates/yaoplm-formats/tests/opl_oracles.rs`, в CI — задание `oracles`.
- **`USBA_crc32`:** тестовые векторы двух видов.
  1. Реальные пары «имя игры → CRC» из имён чанков `ul.XXXXXXXX.*` на флешке, подготовленной OPL Manager или USBUtil (пользователь присылает список файлов, сами игры не нужны). Пока таких нет; есть 4 вектора из тестов ulmake (research/08 §4).
  2. Значения от C-функции из `src/system.c` OPL, скомпилированной в тестовом харнессе на 5000+ случайных именах. `cc` — только dev-зависимость. Код OPL (AFL) в репозиторий не попадает: тест берёт его из клона (`YAOPLM_OPL_SRC`), CI скачивает файлы на зафиксированном коммите.
- **`ul.cfg`:** сравнение с `ul.cfg`, созданным OPL Manager (присылает пользователь).
- **CFG:** round-trip 40 860 реальных CFG из комьюнити-баз (Tom-Bruise, VTSTech) без изменений, плюс правка одного ключа не трогает остальные (`tests/corpus.rs`, нужен `YAOPLM_TESTDATA`). Редактор настроек (CFG-2) на тех же файлах и на 70 CFG GDX-X: без правок файл не меняется ни на байт, переключение режима трогает только `$Compatibility` и `$ConfigSource`, старые биты 0.9.3 остаются.
- **VMC:** пустая карта 8/16/32/64 МиБ совпадает побайтно (кроме времени в корне) с картой `pc/genvmc` OPL, собранного из клона (`opl_oracles.rs`, в CI — задание `oracles`); mymcplusplus проверяет наши карты (`check`, `df`, `ls`) и пишет в них каталог сохранения; суперблоки карт genvmc из ps2vmc-tool (`samples/oplcard.bin`, `card16mb.bin`, `card32mb.bin`, в репозиторий не попадают) совпадают с нашими (`vmc_oracles.rs`, нужен `YAOPLM_TESTDATA`).
- **Фрагменты файла:** `crates/yaoplm-device/tests/fragments.rs` считает куски настоящих файлов только на чтение (`YAOPLM_FRAGMENT_FILES`), для сверки с `fsutil file queryextents`. На флешке владельца (FAT32) части ul и `ul.cfg` — по одному куску, как и у `fsutil` (повторено 2026-10-24: пять частей GTA SA, по одному куску). Там же `fragments_on_real_drivers`: на подключённом образе FAT32/exFAT пишет файл одним проходом (один кусок) и два файла поочерёдно по кластеру (много кусков); `YAOPLM_FRAGMENTS_KNOWN=1` или `0` требует, чтобы ОС сказала или не сказала. CI: задача `real-fs` гоняет его без root (`0`) и под root через `sudo -E` (`1`: файл одним проходом — 1 кусок, поочерёдные — по 16), задача `real-fs-macos` — на образах `hdiutil` (macOS 15 пока не сообщает раскладку ни FAT32, ни exFAT; тест принимает оба исхода и печатает его). Правила OPL и предупреждения проверяет `crates/yaoplm-core/tests/fragments.rs` на `MemFs::set_fragments`.
- **CHT:** разбор 3 629 файлов OPL-Widescreen-Cheats (`tests/corpus.rs`).

- **Профиль загрузчика (LIB-1):** признаки и их порядок — модульные тесты `crates/yaoplm-core/src/detect.rs` на `MemFs` (контрольная сумма с подменной таблицей, файлы семейств, `games.bin` обоих поколений, ключи `conf_opl.cfg`, exFAT/ZSO, спорящие загрузчики); переопределение, явный `--profile` и ключ носителя — `the_loader_profile_of_a_device` в `crates/yaoplm-api/tests/plans.rs`; вывод CLI — `devices_and_device_doctor`; интерфейс — `web/tests/e2e/loader.spec.ts` (кладёт `settings_riptopl.cfg` в фикстуру на время теста) и `web/tests/unit/settings.test.ts` (старая глобальная настройка не действует, ADR-0040).
- **Режим носителя (ADR-0047):** место → режим (в том числе USB-диск с NTFS → по сети, NTFS-флешка → в консоль) — `crates/yaoplm-device/src/mode.rs`; «мало места» на томах владельца 2026-10-25 — `little_free_space_in_either_mode` в `advice.rs`; доктор в режиме SMB (системная папка без ошибок, FAT32 на компьютере → `ul`, RiptOPL → SMB2, корень системного диска → предупреждение, только чтение → ошибка) и неизменный режим PS2 — `advice.rs`; копии файлов загрузчика — `what_the_console_wrote_and_what_was_copied` в `detect.rs`; папка библиотеки в корне — `init_folder_makes_a_library_inside_the_root` в `crates/yaoplm-core/tests/ops.rs`; через API (режим по месту, переопределение, явный режим, вопрос в пустой папке, причина «копия», корень сервера, `PlanInit` с `folder`) — `a_folder_on_the_computer_is_read_over_smb` и `a_library_folder_inside_the_root` в `crates/yaoplm-api/tests/plans.rs`; CLI `--mode` — `devices_and_device_doctor`; интерфейс — `DeviceMode.test.tsx` и `LoaderProfileHint.test.tsx` (строка подключения и её переключатель, «Создать папки OPL», «Создать папку…», только предупреждение на сервере, вопрос в пустой папке для SMB) и `loader.spec.ts`. Временные папки тестов лежат на диске компьютера, поэтому получают режим SMB; тесты, которым нужен носитель для PS2, передают `mode: "ps2"` (CLI `--mode ps2`) или включают его переключателем. Определение профиля режим не меняет: `loader_corpus` даёт те же результаты. Таблица хешей OPL 1.0.0/1.1.0 проверена на настоящем ELF из официального архива (`$YAOPLM_TESTDATA\downloads\opl-v1.1.0\`). Версия внутри ELF — модульные тесты `crates/yaoplm-formats/src/ps2_elf.rs` (упакованные и неупакованные ELF, обрезанные и испорченные копии); на настоящих сборках — `loader_elfs` (451 ELF из 98 релизных ассетов OPL, форков, NHDDL и Neutrino; версии сверяются со списком из имён релизов и истории git; на каждую папку релиза — испорченные копии: обрезка, заголовки, свойства LZMA, байты потока) и `loader_corpus` (определение на тех же ELF: чистая установка, переименованный ELF, остатки другого форка, обрезанный файл, два ELF разных поколений). Выборка собирается `scripts/loader-corpus.py`, только в `$YAOPLM_TESTDATA\downloads\loaders`. Fuzz-цель `ps2_elf`.

## Сбои и восстановление

`crates/yaoplm-core/tests/recovery.rs` (ADR-0021):
- флешка «выдернута» посреди третьего чанка игры на 4,4 ГБ → откат по журналу не оставляет ни одного `ul.*`, докат даёт пять верных чанков и `ul.cfg`;
- прерванное восстановление запускается снова и доводится до конца;
- отмена откатывает только текущую игру; сбой записи `ul.cfg` удаляет уже записанные чанки;
- сбой после точки фиксации (удаление `games.bin`) докатывается даже при выборе «откат»;
- от журнала осталась только временная копия `.json.yaoplm-tmp` (на FAT замена файла — это удаление старого и переименование нового, research/09 §5.3): сканирование видит незавершённую операцию, очистка перед записью возвращает журнал на место, восстановление откатывает;
- повреждённый журнал (байт не на месте в hex-содержимом) — «журнал не читается», а не паника;
- откат меняет только своё: `ul.cfg`, который после сбоя изменил OPL или другой менеджер, остаётся (`notRestored`); CFG, который лежал на месте копии до неё, не удаляется;
- возобновлённое восстановление удаляет `games.bin`, даже если откатилась игра, с которой было связано это удаление.

`crates/yaoplm-core/tests/ops.rs`: файл, который пользователь заменил после составления плана удаления, остаётся (`changedKept`). `crates/yaoplm-device/src/fs.rs`: `sync_dir` открывает и сбрасывает папку на любой ОС (на Windows — ещё и корень тома). На настоящем драйвере FAT32 под Windows это проверяет `real_fs` на тестовой флешке владельца в отдельной папке (`YAOPLM_FAT32_DIR=<флешка>\yaoplm-realfs-test`, только после сверки серийного номера тома; папку потом удалить).

exFAT-образ локально не проверить: нет Rust-библиотеки, которая пишет файлы в exFAT (`exfat-fs` 0.1 только читает и форматирует). Логику exFAT покрывает `MemFs`, настоящий драйвер — задание CI `real-fs` на Linux.

## Fuzz и property-тесты

- `crates/yaoplm-formats/tests/properties.rs` (proptest, в обычном `cargo test`): CFG без потерь, `set` не трогает чужие ключи, `ul.cfg` и ZSO round-trip, парсеры не падают на мусоре; в CUE позиции остаются в пределах диска при любых минутах, а номер строки в ошибке — номер настоящей строки при любых концах строк. Переполнение — не сравнение, и libFuzzer мутации к нему не ведёт: цель `cue` нашла переполнение минут только с граничными числами в словаре, поэтому позиции проверяет и proptest на каждом прогоне.
- `fuzz/` (cargo-fuzz, nightly): цели `iso`, `system_cnf`, `cfg`, `ul_cfg`, `zso`, `cht`, `tar`, `ps2_elf` и `cue` с теми же инвариантами. В CI раз в неделю (`fuzz.yml`), в обычном CI только проверка сборки. Цель `iso` стартует с корпуса фикстур (`write_fixtures`), у цели есть словарь, если лежит `fuzz/dict/<цель>.dict`. Запуск всегда с `-a` (проверки переполнения): с одним `-O` переполнение тихо заворачивается, и 2026-10-26 цель `cue` с `-O` не нашла за 1,2 млн прогонов то, что с `-O -a` нашла за три минуты. На Windows — с `--no-include-main-msvc` (`fuzz/build.rs` объясняет почему).

## Тестовый диск для консоли

## Тестовые данные вне репозитория

Папка `yaoplm-testdata` в корне одного из дисков владельца (не в git). Буквы дисков меняются с тем, что подключено, поэтому документация пишет её как `$YAOPLM_TESTDATA`. `. scripts/testdata.ps1` находит её по имени, задаёт `YAOPLM_TESTDATA` и `YAOPLM_OPL_SRC` и перечисляет тома с серийными номерами; в Git Bash — `eval "$(powershell -NoProfile -File scripts/testdata.ps1 -Bash)"`. В корне того же диска лежат личные файлы владельца: вне `yaoplm-testdata` ничего не читаем и не пишем.
```
$YAOPLM_TESTDATA\
├─ iso\         # собственные дампы пользователя (не скачиваются агентом)
├─ homebrew\    # свободные homebrew-ELF/ISO для тестов
├─ opl\         # официальные сборки OPL с GitHub releases (1.1.0 и 1.2.0 beta), справочно
├─ loaders\     # файлы официальных релизов для ручных проверок установщика (LDR-1…LDR-7): <сборка>-<тег>\<ассет>, скачаны с разрешения владельца
├─ images\      # образы FAT32/exFAT для интеграционных тестов
├─ refs\        # клоны эталонных репозиториев (ADR-0015, research/REFERENCES.md)
└─ out\         # результаты прогонов
```
Тесты, которым нужны реальные данные, помечены `#[ignore]` и запускаются только при заданной переменной `YAOPLM_TESTDATA`.

Имена картинок из резервных копий OPL Manager (ART-5): `oplm-art\<item>.tsv` — оглавления копий с archive.org, их пишет `python scripts/oplm-backup-toc.py OPLM_ART_2024_09 OPLM_ART_2023_07` в `$YAOPLM_TESTDATA\oplm-art` (только центральный каталог zip, около 8 МБ на копию, без картинок). Тест: `cargo test -p yaoplm-formats --test oplm_backups -- --ignored --nocapture`.

Покрытие источников картинок (ART-1, ADR-0035): `art-lists\` — списки файлов xlenore и libretro, их пишет `python scripts/art-source-lists.py` в `$YAOPLM_TESTDATA\art-lists` (пять запросов, без картинок), и оглавление `oplm-art\OPLM_ART_2024_09.tsv`. Тест `cargo test -p yaoplm-api --test art_coverage -- --ignored --nocapture` печатает таблицу покрытия по типам и регионам тем же кодом, что выбирает источники (research/14 §1, §6).

Живая проверка источников картинок (вручную, перед релизом или когда источник ведёт себя странно, не в CI): `YAOPLM_LIVE=1 cargo test -p yaoplm-net --test live -- --ignored --nocapture` — оглавление копии OPL Manager и все типы DOA2 в трёх регионах с archive.org, xlenore, libretro, ScreenScraper при ключе.

Сеть в тестах: все тесты работают на зеркалах и локальных серверах; CI и сервер e2e ставят `YAOPLM_OFFLINE=1`, и HTTP-клиент отказывает любому хосту, кроме этого компьютера, поэтому тест, забывший зеркало, падает, а не уходит в интернет.

**Агент не скачивает коммерческие образы игр**, даже маленькие. Скачивать можно: официальные релизы OPL, открытые инструменты (`ziso.py`, hdl-dump и т.п. из исходников), homebrew, открытые базы данных. Для проверки на консоли без коммерческих игр собираем свой тестовый ISO из открытого homebrew-ELF с `SYSTEM.CNF`; с файлом-заполнителем он же проверяет нарезку `ul` (> 4 ГиБ).

### Сессии с устройствами владельца (договорённость 2026-10-24)

Владелец продукта подключит к машине разработчика флешки и microSD эмулятора карты памяти («PSX Memory Card»), на которой с завода есть FreeMcBoot и OPL, а позже — всё остальное из таблицы выше. Цель — научить YAOPLM распознавать разные раскладки носителей и работать с тем, что на них уже лежит, и проверить это на консоли. Порядок:
1. **Опись только на чтение.** Для каждого носителя: таблица разделов, ФС, кластер, серийный номер тома, дерево папок, файлы загрузчиков (ELF, `title.cfg`, файлы настроек) и служебные файлы эмулятора. Заводскую раскладку microSD эмулятора записать до любых изменений: она эталон для LDR-1, LDR-3 и LDR-4 (MMCE). Итог — в `docs/research/` (списки файлов, размеры, хеши; сами ELF, образы карт и прошивки в репозиторий не попадают) и, где нужно, в фикстуры тестов.
2. **Запись — только по плану.** Установка разных сборок OPL (OPL 1.1.0, 1.2.0 beta, YAOPL, RiptOPL) на флешки и смена одной сборки на другую (LDR-3, LDR-4) — через планы YAOPLM, с подтверждением владельца и повторной проверкой серийного номера перед каждой записью. Служебные файлы эмулятора (`.sd2psx/`, `MemoryCards/`, `PS1/`, `PS2/`, `mcp2.bin`, `os/` и то, что найдётся при описи) не трогаем никогда.
3. **Проверка на консоли** по матрице ниже; результаты и замечания — в `docs/testing/`.

## Что нужно от пользователя

1. PS2 с OPL 1.2.0 beta (последняя сборка). Желательно ещё OPL 1.1.0, на второй флешке или через выбор при запуске.
2. Флешки: одна в FAT32, одна в exFAT, от 8 ГБ. Одну флешку можно переформатировать между проверками.
3. Модель и версия прошивки эмулятора карты памяти; объём и ФС SD-карт в эмуляторе и в MX4SIO (агент может посмотреть их только на чтение).
4. Дампы **своих** дисков в `$YAOPLM_TESTDATA\iso\`:
   - CD-игра (синяя сторона диска);
   - DVD-игра до 4 ГиБ;
   - игра больше 4 ГиБ (DVD-9 или крупный DVD-5);
   - позже PS1-игра в BIN/CUE и, если есть, многодорожечная.
5. По возможности флешка, подготовленная OPL Manager: нужен список файлов и `ul.cfg` для эталонов. Если её нет, эталон `USBA_crc32` берём из C-функции OPL, скомпилированной в тесте.
6. Позже: сетевой адаптер для SMB и HDD для внутреннего диска (fat PS2).
