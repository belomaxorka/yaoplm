## Фикстуры

- **Реальные игры в репозиторий не коммитим никогда.** Фикстуры генерирует код в `yaoplm-test-support` (свой генератор ISO9660, ADR-0016; готовые варианты `SYSTEM.CNF` — `Variant`):
  - крошечный ISO9660 с `SYSTEM.CNF` (`BOOT2 = cdrom0:\SLUS_200.62;1`) и пустым ELF;
  - варианты без `BOOT2`, с другим регистром, с длинным ID;
  - BIN/CUE (сырые 2352-байтные секторы) из того же ISO;
  - ZSO из того же ISO;
  - мини-DAT в формате Logiqx;
  - образ FAT32 на несколько МБ (`FatImage`, через `fatfs`);
  - `VirtualFile`/`VirtualIso`: поток на 4,5 ГиБ, генерируемый на лету, для тестов нарезки; `VirtualSources` подставляет такие файлы как источники импорта;
  - `MemFs`: устройство в памяти с семантикой FAT (имена без учёта регистра, лимит 4 ГиБ − 1, свободное место), большие файлы хранятся «пробами» по 16 байт через каждый МиБ, `unplug_after(n)` имитирует выдернутую флешку, `fail_once` — сбой одной операции;
  - `bincue`: BIN/CUE во всех четырёх режимах секторов (MODE1/2048, MODE1/2352, MODE2/2336, MODE2/2352), с паузой перед дорожкой и без.
- Эталоны (golden) лежат в репозитории как маленькие бинарные файлы. В `.gitattributes` они помечены `binary`, чтобы CRLF в CFG не портился.

## Перекрёстные проверки

- **ZSO:** `ziso.py` из репозитория OPL распаковывает наши файлы (`align` 0 и 2), а мы читаем его файлы (`-c 1` и `-c 9`). Тест `crates/yaoplm-formats/tests/opl_oracles.rs`, в CI — задание `oracles`.
- **`USBA_crc32`:** тестовые векторы двух видов.
  1. Реальные пары «имя игры → CRC» из имён чанков `ul.XXXXXXXX.*` на флешке, подготовленной OPL Manager или USBUtil (пользователь присылает список файлов, сами игры не нужны). Пока таких нет; есть 4 вектора из тестов ulmake (research/08 §4).
  2. Значения от C-функции из `src/system.c` OPL, скомпилированной в тестовом харнессе на 5000+ случайных именах. `cc` — только dev-зависимость. Код OPL (AFL) в репозиторий не попадает: тест берёт его из клона (`YAOPLM_OPL_SRC`), CI скачивает файлы на зафиксированном коммите.
- **`ul.cfg`:** сравнение с `ul.cfg`, созданным OPL Manager (присылает пользователь).
- **CFG:** round-trip 40 860 реальных CFG из комьюнити-баз (Tom-Bruise, VTSTech) без изменений, плюс правка одного ключа не трогает остальные (`tests/corpus.rs`, нужен `YAOPLM_TESTDATA`).
- **CHT:** разбор 3 629 файлов OPL-Widescreen-Cheats (`tests/corpus.rs`).

## Сбои и восстановление

`crates/yaoplm-core/tests/recovery.rs` (ADR-0021):
- флешка «выдернута» посреди третьего чанка игры на 4,4 ГБ → откат по журналу не оставляет ни одного `ul.*`, докат даёт пять верных чанков и `ul.cfg`;
- прерванное восстановление запускается снова и доводится до конца;
- отмена откатывает только текущую игру; сбой записи `ul.cfg` удаляет уже записанные чанки;
- сбой после точки фиксации (удаление `games.bin`) докатывается даже при выборе «откат».

exFAT-образ локально не проверить: нет Rust-библиотеки, которая пишет файлы в exFAT (`exfat-fs` 0.1 только читает и форматирует). Логику exFAT покрывает `MemFs`, настоящий драйвер — задание CI `real-fs` на Linux.

## Fuzz и property-тесты

- `crates/yaoplm-formats/tests/properties.rs` (proptest, в обычном `cargo test`): CFG без потерь, `set` не трогает чужие ключи, `ul.cfg` и ZSO round-trip, парсеры не падают на мусоре.
- `fuzz/` (cargo-fuzz, nightly): цели `iso`, `system_cnf`, `cfg`, `ul_cfg`, `zso`, `cht` с теми же инвариантами. В CI раз в неделю (`fuzz.yml`), в обычном CI только проверка сборки. Цель `iso` стартует с корпуса фикстур (`write_fixtures`).

## Тестовый диск для консоли

`cargo run -p yaoplm-test-support --example make_boot_iso -- --elf <ELF> --out <ISO> [--min-mib 4300]` собирает загрузочный образ из открытого homebrew-ELF (ID `YAOP_000.01`). Используем wLaunchELF из официального релиза, он лежит в `D:\yaoplm-testdata\homebrew\wLaunchELF\` вместе с `SOURCE.txt` (источник, лицензия, SHA-256). Вариант больше 4 ГиБ (`--min-mib 4300`) — для проверки `ul` на FAT32 в M2.

## Проверка интерфейса агентом

1. Фикстурная библиотека: `cargo run -p yaoplm-api --example make_library -- <папка> [--games N]` создаёт `<папка>/library` (игры во всех форматах, CFG, предупреждения, файлы, которые OPL не видит, одна игра с обложкой), `<папка>/sources` (образы для импорта) и `<папка>/mirror` (зеркала источников обложек: `xlenore/covers/default/SLUS-20062.jpg`, `libretro/Named_Boxarts/<имя Redump>.png`, плюс `custom-cover.jpg` для ручной замены). Ничего настоящего: все образы и картинки сгенерированы. `--games 3000` — для проверки виртуализации.
2. Превью через `.claude/launch.json`: `yaoplm-server-fixture` (7878; `web/tests/e2e/server.mjs` сам строит фикстуру во временной папке и запускает сервер с двумя корнями) плюс `web-dev` (Vite, 5173, проксирует `/api`). Для сервера без Vite нужен `pnpm -C web build`.
3. Playwright (`web/tests/e2e/`, `pnpm -C web e2e`): тот же скрипт поднимает сервер на 7879 на свежей фикстуре; тесты идут по одному, потому что делят библиотеку. `library.spec.ts` проходит сценарий U1: устройство → игры → поиск и фильтры → карточка → добавить игру через обзор папок сервера → план с переопределением названия → подтверждение → задание и его журнал → игра в списке → переименование → удаление с отдельным подтверждением. `art.spec.ts` проходит обложки (ART-1…ART-4, META-1): счётчик «без обложки», название из базы, загрузка одной обложки из карточки, массовая «только недостающие» (пропускает игры с обложкой, перечисляет ненайденные), ручная замена файлом из папок сервера, удаление с подтверждением, экран «О программе». Источники читают зеркала фикстуры через настройки (`openLibrary` в `helpers.ts`), сервер поднят с `--data-dir` во временной папке: ни одного запроса в интернет. `screenshots.spec.ts` снимает устройства, библиотеку (уже с обложками), карточку, диалог плана, добавление, план импорта, диалог загрузки обложек, задания и настройки в обеих темах, на `en` и `ru`, при ширине 1280 и 800 (`web/test-results/screenshots/`, в CI — артефакт `playwright`).
4. Десктоп: `pnpm tauri dev` на Windows; диалоги выбора файлов и drag-and-drop есть только там.

## Тестовые данные вне репозитория

Каталог `D:\yaoplm-testdata\` (на D: больше места; не в git):
```
D:\yaoplm-testdata\
├─ iso\         # собственные дампы пользователя (не скачиваются агентом)
├─ homebrew\    # свободные homebrew-ELF/ISO для тестов
├─ opl\         # официальные сборки OPL с GitHub releases (1.1.0 и 1.2.0 beta), справочно
├─ images\      # образы FAT32/exFAT для интеграционных тестов
├─ refs\        # клоны эталонных репозиториев (ADR-0015, research/REFERENCES.md)
└─ out\         # результаты прогонов
```
Тесты, которым нужны реальные данные, помечены `#[ignore]` и запускаются только при заданной переменной `YAOPLM_TESTDATA=D:\yaoplm-testdata`.

**Агент не скачивает коммерческие образы игр**, даже маленькие. Скачивать можно: официальные релизы OPL, открытые инструменты (`ziso.py`, hdl-dump и т.п. из исходников), homebrew, открытые базы данных. Для проверки на консоли без коммерческих игр собираем свой тестовый ISO из открытого homebrew-ELF с `SYSTEM.CNF`; с файлом-заполнителем он же проверяет нарезку `ul` (> 4 ГиБ).

## Что нужно от пользователя

1. PS2 с OPL 1.2.0 beta (последняя сборка). Желательно ещё OPL 1.1.0, на второй флешке или через выбор при запуске.
2. Флешки: одна в FAT32, одна в exFAT, от 8 ГБ. Одну флешку можно переформатировать между проверками.
3. Модель и версия прошивки эмулятора карты памяти; объём и ФС SD-карт в эмуляторе и в MX4SIO (агент может посмотреть их только на чтение).
4. Дампы **своих** дисков в `D:\yaoplm-testdata\iso\`:
   - CD-игра (синяя сторона диска);
   - DVD-игра до 4 ГиБ;
   - игра больше 4 ГиБ (DVD-9 или крупный DVD-5);
   - позже PS1-игра в BIN/CUE и, если есть, многодорожечная.
5. По возможности флешка, подготовленная OPL Manager: нужен список файлов и `ul.cfg` для эталонов. Если её нет, эталон `USBA_crc32` берём из C-функции OPL, скомпилированной в тесте.
6. Позже: сетевой адаптер для SMB и HDD для внутреннего диска (fat PS2).
