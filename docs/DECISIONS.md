# Журнал решений (ADR)

Формат: контекст → решение → последствия. Новые решения добавляются в конец. Отменённое решение не удаляется, а помечается `Заменено ADR-XXXX`.

## ADR-0001 — Стек: Tauri 2 + ядро на Rust + React/TS
*2026-10-22, принято.*
- **Контекст.** Нужны Windows, Linux и macOS, один код ядра для GUI, CLI и сервера, быстрая работа с многогигабайтными образами (research/04).
- **Решение.** Tauri 2.12 + Cargo workspace + axum + clap + React 19/TS/Vite.
  - Только в Rust есть поддерживаемые библиотеки без C-зависимостей для CHD, чтения и записи ISO, 7z, SMB2/3 и LZ4.
  - Сборки маленькие, есть официальный CI (`tauri-action`) и updater.
- **Отвергнуто.**
  - Wails v3 (Go): всё ещё beta, нет CHD, SMB-библиотека устарела. Пересмотреть после выхода v3.0.
  - Electron: инсталлятор 120–200 МБ, слабые нативные библиотеки.
  - Avalonia, Flutter, Qt: веб-интерфейс для сервера пришлось бы делать отдельно.
- **Последствия.** Высокий порог входа в Rust. Ядро держим синхронным, линтеры строгие, тестов много.

## ADR-0002 — Лицензия GPL-3.0-or-later
*2026-10-22, принято.*
- **Контекст.**
  - Хотим встроить базу названий, сделанную из PCSX2 GameIndex (GPL-3.0).
  - Родственные проекты (OrbitPS2, OPL PC Tools, PyOPLM) под GPL-3.
  - hdl-dump и pfsshell под GPL-2.
- **Решение.** GPL-3.0-or-later.
- **Последствия.**
  - Код GPL-3-проектов можно заимствовать с сохранением авторства.
  - Код OPL (AFL-3.0) и ps2sdk (AFL-2.0) используем как справочник по форматам; копирование кода нужно проверять отдельно.
  - GPL-2-only инструменты допустимо запускать только как отдельные процессы.

## ADR-0003 — Синхронное ядро, асинхронность только на краях
*2026-10-22, принято.* Крейты `core`, `formats`, `hash` и `device` не зависят от tokio, tauri и axum, что проверяется в CI. Так проще писать, тестировать и ревьюить код.

## ADR-0004 — Целевой загрузчик по умолчанию: OPL 1.2.0 beta
*2026-10-22, принято.*
- Последний stable OPL — v1.1.0 (2021). Пользователи в основном сидят на rolling-сборке 1.2.0 beta: exFAT, ZSO, PNG-only обложки.
- Профиль по умолчанию — 1.2.0 beta. Профили 1.1.0 и RiptOPL меняют правила (SPEC §4).

## ADR-0005 — Обложки всегда в PNG
*2026-10-22, принято.* OPL 1.2 beta читает только PNG (коммит c5a12a0), а 1.1.0 читает PNG, JPG и BMP. Значит, PNG подходит обоим. Размер ≤1024 px.

## ADR-0006 — Формат имени по умолчанию: `ID.Title.iso`
*2026-10-22, принято.* Если имя в старом формате (`SLUS_200.62.Title.iso`), OPL берёт ID из имени и не монтирует образ при сканировании: это быстрее и совместимо с 1.1.0. Формат `Title.iso` остаётся как опция.

## ADR-0007 — Политика источников данных
*2026-10-22, принято.*
- Приватный сервер обложек OPL Manager не используем: у него нет публичного API и условий использования.
- Изображения в сборку не включаем.
- Встраиваем только данные с совместимой лицензией (GameIndex — GPL-3.0, libretro-database — CC BY-SA 4.0) и указываем авторство.
- Источники без лицензии (xlenore/ps2-covers, compat-листы) используем только во время работы, по запросу пользователя, с кэшем.

## ADR-0012 — Защита API сервера
*2026-10-22, принято.* Уточняет ADR-0009.
- **Контекст.** Сервер на 127.0.0.1 без токена доступен любому сайту, открытому в браузере пользователя. Простой кросс-сайтовый POST (форма или `text/plain`) уходит без CORS-preflight, а DNS rebinding позволяет ещё и читать ответы. Начиная с M2, через API можно будет менять и удалять файлы.
- **Решение.** Для `/api/*`:
  - `POST /api/rpc` принимает только `Content-Type: application/json`. Кросс-сайтовый запрос с таким типом требует preflight, а мы его не обслуживаем.
  - Если пришёл заголовок `Origin`, он должен совпадать с `Host`.
  - Сервер на loopback **без токена** принимает только loopback-`Host` (`localhost`, `127.x.x.x`, `[::1]`). С токеном эта проверка не нужна: токен через DNS rebinding не подделать. Поэтому за reverse proxy сервер может слушать 127.0.0.1.
  - Токен передаётся в `Authorization: Bearer`. Только для WebSocket `/api/events` допускается `?token=`, потому что браузер не умеет слать заголовки при handshake.
  - UI получает токен один раз через адрес `/?token=…`: сохраняет его в localStorage и убирает из адресной строки.
  - Токен сравнивается за постоянное время.
- **Последствия.**
  - Reverse proxy должен передавать исходный `Host` (Caddy делает это по умолчанию, в nginx нужно `proxy_set_header Host $host`). Иначе `Origin` не совпадёт с `Host`.
  - Доступа к API с другого origin нет. Если понадобится, добавим явный allow-list.

## ADR-0013 — Форматирование съёмных носителей с защитой от ошибки
*2026-10-22, принято по запросу владельца продукта. Заменяет ADR-0008.*
- **Контекст.** Пользователю нужна подготовка носителя с нуля: флешка или SD-карта для MX4SIO и эмулятора карты памяти. Неправильная ФС, разметка или размер кластера — частая причина того, что OPL не видит игры или тормозит. Риски из ADR-0008 никуда не делись: ошибка уничтожает данные, а повышение прав в каждой ОС своё.
- **Решение.** Форматирование входит в продукт (SPEC DEV-3, DEV-4) с такими ограничениями:
  - Только съёмные диски на USB или SD-шине. Системный и загрузочный диск, а также диски с примонтированной ОС, недоступны вообще.
  - Перед планом показываем модель, серийный номер, размер, текущие разделы и метки томов.
  - Подтверждение вводом (например, метки или размера диска), а не одной кнопкой.
  - Прямо перед записью диск проверяется ещё раз по тому же идентификатору: если он сменился или переподключился, операция отменяется.
  - Запись выполняет отдельный процесс-помощник с повышенными правами (`yaoplm helper --stdio`), а не основной процесс.
  - Параметры (ФС, MBR/GPT, кластер, выравнивание) берутся из профиля носителя и загрузчика, пользователь может их изменить.
  - В автотестах форматируем только файлы-образы, никогда реальные диски.
- **Последствия.** Появляется самая опасная операция в продукте, поэтому её код отдельно ревьюит владелец и проверяет на своих носителях. Этап — v0.2: до этого остаётся диагностика носителя только на чтение (DEV-2).
- **Уточнение по research/06 (2026-10-22).**
  - Доступ к диску: повышенные права нужны только на Windows (помощник через UAC и защищённый именованный канал). На Linux непривилегированный помощник получает дескриптор устройства через udisks2 (один запрос polkit), на macOS — через `authopen` (нужен прототип). В режиме сервера и в Docker форматирования нет.
  - Подтверждение вводом — размер диска.
  - Сначала пишем файловую систему, таблицу разделов — последней; идентичность диска проверяем через тот же дескриптор, которым пишем.
  - Только диски с логическим сектором 512 байт: FatFs в OPL собран с `FF_MAX_SS 512` (проверено в `fjtrujy/FatFs` ветка `iop-r0.16`).
  - Выбор движка (свой exFAT или системный на Windows и macOS) зависит от вопроса о патентах exFAT — SPEC, открытый вопрос 6.

## ADR-0014 — Установка загрузчиков только с официальных релизов
*2026-10-22, принято.* Дополняет ADR-0007.
- **Контекст.** Владелец хочет ставить из программы разные сборки: официальный OPL, RiptOPL, форк с MMCE и другие (SPEC LDR-1…5). Бинарники PS2-программ меняются часто, у них разные лицензии.
- **Решение.**
  - Скачиваем только с официальных релизов проектов (GitHub Releases и аналоги), по явному действию пользователя. В сборку YAOPLM бинарники загрузчиков не входят.
  - Фиксируем сборку по SHA-256 ассета, а не по тегу: «плавающие» теги вроде `latest` перезаписываются на месте. Хеш берём из GitHub API, если релиз его публикует, иначе считаем и показываем свой. Кэшируем, показываем лицензию и ссылку на исходники.
  - Конфиги способов запуска (FreeMcBoot, PS2BBL) не пишем, а показываем пользователю строки для них (SPEC BOOT-1).
  - Можно установить из своего архива без сети.
  - Эксплойты (FreeMcBoot, PS2BBL) на физическую карту памяти не ставим.
- **Последствия.** Каталог загрузчиков — данные, которые обновляются без выпуска новой версии программы. Когда меняется формат релизов какого-то проекта, достаточно поправить его запись в каталоге.

## ADR-0015 — Эталонные проекты как источник граничных случаев
*2026-10-22, принято.*
- **Контекст.** В исходниках OPL, его форков и соседних программ годами копились исправления для особых случаев, ошибок железа и прошивок. Многие из них нигде не описаны, кроме комментариев в коде, коммитов и issues. Искать их по форумам долго.
- **Решение.**
  - Ведём справочник репозиториев `docs/research/REFERENCES.md` и их локальные клоны в `D:\yaoplm-testdata\refs\<owner>__<repo>`.
  - Перед реализацией формата или работы с устройством читаем соответствующий код в официальном OPL и форках, их коммиты и issues; при необходимости — ветки форумов (psx-place читаем через Chrome пользователя).
  - Сравниваем реализации. Эталон поведения — официальный OPL (CLAUDE.md: «Follow OPL source»); форки и другие менеджеры — источник граничных случаев и исправлений, которые проверяем, прежде чем переносить. В комментарии к нашему коду указываем файл и коммит источника.
  - Лицензии: код OPL (AFL-3.0) и ps2sdk (AFL-2.0) не копируем, а переписываем по смыслу (ADR-0002). Код под GPL-3-совместимыми лицензиями можно переносить с указанием авторства.
- **Последствия.** Справочник нужно поддерживать в актуальном состоянии (`git pull` по клонам), а находки — записывать в research/.

## ADR-0016 — Свой ридер ISO9660 и генератор фикстур вместо hadris-iso
*2026-10-22, принято в M1.* Уточняет стек в ARCHITECTURE.md §2.
- **Контекст.** ID игры должен совпадать с тем, что покажет OPL (IMP-2). isofs в OPL намного строже стандарта: читает только сектор 16, ищет в корне ровно `SYSTEM.CNF;1` через `strcmp` (с учётом регистра, версии `;1` и байта-заполнителя), обрабатывает записи нулевой длины по-своему (research/08 §3). Универсальная библиотека находит файл там, где OPL его не видит, и скрывает от нас причину. Для тестов нужны «неправильные» образы (без `;1`, с именем в нижнем регистре, со вторым PVD для DVD-9, больше 4 ГиБ без места на диске), а стандартные писатели такие не делают.
- **Решение.**
  - `yaoplm-formats::iso9660` — свой минимальный ридер, повторяющий логику isofs OPL (PVD, поиск в корне, чтение файла, проба слоя DVD-9), плюс простой стандартный листинг каталогов для отображения.
  - `yaoplm-test-support::iso` — свой генератор ISO9660 (PVD, терминатор, таблицы путей, каталоги, файлы), отдающий образ потоково через `Read + Seek`.
  - `hadris-iso` пока не подключаем. Вернёмся к нему, если понадобится полноценная запись ISO (например, BIN/CUE → ISO в IMP-1 можно сделать и без неё: это копирование секторов данных).
- **Последствия.** Около 600 строк своего кода, зато каждое правило покрыто тестом и fuzz-целью. ZSO-ридер встроен в тот же интерфейс `SectorSource`, поэтому все проверки работают одинаково для ISO, ZSO и цепочки чанков `ul`.

## ADR-0017 — Ветки вех вливаются обычным merge-коммитом
*2026-10-22, принято по предложению владельца продукта.*
- **Контекст.** PR вех (M0, M1…) содержат десятки осмысленных коммитов с ID требований. При squash история схлопывается в один коммит: теряются `git blame` по конкретному правилу и `git bisect` до коммита.
- **Решение.** PR вех и крупных задач вливаются через «Create a merge commit». Маленькие PR из одного логического изменения (например, только документы) можно вливать squash.
- **Последствия.** Каждый коммит в ветке должен собираться и проходить тесты сам по себе. Мелкие исправления («fix typo», правки clippy) агент вливает в исходные коммиты до открытия PR (`git commit --fixup` + `git rebase --autosquash`). Короткую историю по PR даёт `git log --first-parent main`.

## ADR-0018 — Свой форк OPL для исправления найденных багов
*2026-10-22, принято по решению владельца продукта.*
- **Контекст.** В M1 нашлись баги OPL на «кривых» входных данных (research/08 §10). Три из них не исправлены ни в upstream, ни в одном форке: чит с пустым именем из комментария с отступом, зависание на записи каталога ISO с пустым именем, деление на ноль в ZSO при `align > 11`. Ещё пять исправлены только в RiptOPL. Upstream развивается медленно, хотя PR сообщества принимает.
- **Решение.**
  - Форк `ps2homebrew/Open-PS2-Loader` под аккаунтом владельца, отдельный репозиторий. Лицензия форка — AFL-3.0, как у OPL. Код YAOPLM (GPL-3) в форк не копируем, код форка в YAOPLM — тоже нет (ADR-0002).
  - Своя линия развития: исправления коммитим прямо в форк, а не готовим как PR в upstream. Изменения upstream периодически подтягиваем в форк. Отправка отдельных исправлений в upstream возможна, но не обязательна и только с одобрения владельца.
  - Автоматическая сборка в GitHub Actions форка на каждый пуш в основную ветку, с публикацией готового ELF (по образцу rolling-релиза `latest` в upstream), чтобы владелец ставил наш OPL с исправлениями на консоль.
  - Исправления RiptOPL переносим выборочно: только реальные баги и только после проверки «до/после» на воспроизводящих входных данных. Авторство указываем (та же лицензия AFL-3.0).
  - Проверка — на консоли владельца и на фикстурах `yaoplm-test-support`; чисто логические функции (разбор CHT, `SYSTEM.CNF`, `ul.cfg`) дополнительно проверяем, собирая их на PC в тестовом стенде.
  - Как только форк начнёт выпускать сборки, добавим в YAOPLM профиль загрузчика для него (правила форматов пока совпадают с upstream).
- **Последствия.** Появляется второй репозиторий со своим циклом и обязанность подтягивать upstream. YAOPLM по-прежнему не полагается на исправления: менеджер не создаёт «кривые» данные и предупреждает о них при сканировании, потому что у пользователей может стоять любой загрузчик.

## ADR-0019 — Тома и предвыделение через API ОС, `unsafe` только в одном модуле
*2026-10-22, принято в M2.* Уточняет стек в ARCHITECTURE.md §2 и §8.
- **Контекст.** Для DEV-1/DEV-2 и для повторной проверки носителя перед записью нужны серийный номер тома, размер кластера и сектора, шина (USB/SD), таблица разделов и смещение раздела, а для записи (IMP-7) — предвыделение места. `sysinfo` даёт только точку монтирования, тип ФС, объём и признак «removable» (на Windows это `GetDriveTypeW`, а USB-диски там «fixed»), не видит сетевые диски и не умеет «том по пути». Ни один из найденных крейтов не закрывает всё сразу.
- **Решение.**
  - `yaoplm-device` обращается к ОС напрямую:
    - Windows — `windows-sys` 0.61: `GetVolumeInformationW`, `GetDiskFreeSpace(Ex)W`, `GetVolumePathNameW`, `IOCTL_STORAGE_QUERY_PROPERTY` и `IOCTL_DISK_GET_PARTITION_INFO_EX` на дескрипторе тома с доступом 0 (без прав администратора), предвыделение — `SetFileInformationByHandle(FileAllocationInfo)`;
    - Linux — `/proc/self/mountinfo`, sysfs, `/dev/disk/by-uuid` и `by-label`, `statvfs` и `fallocate(FALLOC_FL_KEEP_SIZE)` через `rustix` 1.1;
    - macOS — `statfs` через `rustix` и `/Volumes`; шина, раздел и серийный номер пока не определяются, предвыделения нет (`F_PREALLOCATE` в rustix ещё и удлиняет файл, а msdosfs заполняет удлинение нулями).
  - `sysinfo` не подключаем.
  - `unsafe` в workspace по-прежнему запрещён (`unsafe_code = "deny"`). Единственное исключение — `crates/yaoplm-device/src/sys/windows.rs`: тонкие обёртки над документированными вызовами Win32, буферы выделяет Rust, у каждого блока комментарий `SAFETY`.
- **Последствия.** Около 300 строк платформенного кода, который CI проверяет на трёх ОС. Подробности для macOS (DiskArbitration или `diskutil`) — позже, вместе с DEV-3.

## ADR-0020 — Переименование меняет то, что OPL связывает с названием; VMC не трогаем никогда
*2026-10-23, принято в M2.* Уточняет SPEC GAME-1 и GAME-2.
- **Контекст.** GAME-1 требовал «синхронно обновлять ART, CFG, CHT и ссылки на VMC» при переименовании. Но OPL называет CFG, ART и CHT по ID игры, а не по названию, и ни OPL, ни его форки, ни соседние менеджеры при смене названия их не трогают (research/09 §4). Карты VMC OPL по умолчанию называет `<ID группы или ID>_<слот>`, есть ещё `generic_0`/`generic_1`: одна карта часто общая для серии игр.
- **Решение.**
  - Новое название меняет только имя образа или, для `ul`, имена чанков (их хеш считается от названия) и запись `ul.cfg`; `games.bin` в папке удаляется.
  - CFG (и `.info` wOPL), `ART/<ID>_*` и `CHT/<ID>.cht` переносятся только когда меняется действующий ID: пользователь исправил ID в имени старого формата или в записи `ul.cfg`, либо смена формата имени меняет ID, который возьмёт OPL. Если старый ID есть ещё у другой игры, файлы копируются, а не переносятся. Существующий файл с новым именем останавливает план.
  - Файлы VMC и значения `$VMC_0`/`$VMC_1` не меняются никогда: CFG переезжает целиком и продолжает указывать на ту же карту. Так «ссылки на VMC» сохраняются, а общие карты не ломаются.
  - Удаление по умолчанию стирает только образ (или запись `ul.cfg` и чанки). CFG, обложки и читы — по явному выбору и только если ID не использует другая игра; VMC не удаляется никогда.
  - Каждый CFG перед переносом или удалением копируется в `.yaoplm/backup/<id>/` (CFG-5).
- **Последствия.** Переименование не может испортить настройки другой игры. Удаление сейвов VMC — отдельная функция с отдельным подтверждением (VMC-2, later).

## ADR-0021 — Транзакции с точкой фиксации и журнал на устройстве
*2026-10-23, принято в M2.* Уточняет ARCHITECTURE.md §5.
- **Контекст.** SPEC требует атомарной записи и журнала многошаговых операций с откатом или докатом. Флешку могут выдернуть посреди нарезки 8 ГБ; ни один из изученных менеджеров не переживает такой сбой без мусора на носителе (research/09 §1, §5).
- **Решение.**
  - План — список транзакций (одна игра, одно переименование…), транзакция — список шагов с точкой фиксации. Шаги до неё обратимы. Шаг прямо перед ней делает изменение видимым для OPL: переименование образа на место или запись `ul.cfg`. Шаги после неё только завершают работу: удаление `games.bin`, удаление по просьбе пользователя, удаление источника при переносе.
  - Журнал — JSON в `.yaoplm/journal/<id>.json` в корне устройства: весь план и число выполненных шагов каждой транзакции. Перезаписывается атомарно после каждого шага и удаляется, когда план завершён. OPL корень не показывает, NHDDL пропускает имена с точкой.
  - Сбой или отмена до точки фиксации откатывает транзакцию (новые шаги первыми); после неё журнал остаётся, и восстановление докатывает транзакцию. Незафиксированную транзакцию по выбору пользователя можно не откатить, а повторить. Шаги восстановления идемпотентны, поэтому прерванное восстановление можно запустить снова.
  - Перед первой записью исполнитель повторно проверяет отпечаток тома (серийный номер, ФС, размер, метка), неизменность источников (размер и время изменения), свободное место и отсутствие незавершённых журналов.
  - Планы хранятся на стороне ядра (`PlanStore`); клиент отправляет только id плана. План выполняется один раз и живёт час. План с удалением пользовательских файлов требует явного `confirmDelete`.
  - Задания записи выполняются строго по одному в порядке очереди: параллельная запись на одну флешку фрагментирует обе игры.
- **Последствия.** На носителе появляется папка `.yaoplm` (журналы и резервные копии CFG). Пакет из N игр — N независимых транзакций: сбой на третьей игре оставляет первые две на месте.

## ADR-0022 — Каталог загрузчиков, идентичность сборки по хешу и обновление только в пределах канала
*2026-10-23, принято по запросу владельца продукта.* Уточняет ADR-0014 и ADR-0018; детали — SPEC §5.10.1, источники — research/07.
- **Контекст.** Владелец хочет режим установки загрузчика на носитель (папки по профилю плюс ELF по способу запуска) и обновление: программа определяет, какой загрузчик и какой версии стоит на флешке, и предлагает свежую сборку того же форка, а не другой. Сложности: ELF упакован ps2-packer, версии внутри не видно; плавающие теги (`latest`, `rolling`) перезаписывают ассеты; `digest` GitHub есть только у недавно загруженных файлов; из репозиториев мы контролируем только свой форк YAOPL.
- **Решение.**
  - Каталог сборок — данные в `data/loaders/`, а не код: семейство, канал, репозиторий, лицензия, профиль, ассеты, набор папок, пресеты путей, отпечатки. Обновляется без выпуска новой версии программы.
  - Идентичность сборки — семейство + канал + версия + SHA-256 ELF. История хешей ведётся только дописыванием: для YAOPL — `HASHES.txt`, который дописывает CI форка; для чужих репозиториев — `data/loader-hashes/<id>.txt` у нас, которые раз в сутки дополняет workflow по расписанию из GitHub Releases API; всё скачанное самим YAOPLM запоминается в локальном кэше. Неизвестный хеш — нормальный случай: такая сборка показывается как «семейство X, версия неизвестна».
  - Распознавание по порядку: манифест установки `.yaoplm/manifest.json` → история хешей → `title.cfg` → имена файлов → отпечатки файлов настроек. Результат всегда сопровождается уровнем уверенности.
  - Обновление предлагается только в пределах того же семейства и канала; смена форка, канала или пути ELF — отдельное явное действие «Заменить». Обновление меняет только ELF (и пакет приложения у RiptOPL), держит резервную копию прежнего ELF и умеет откатиться.
  - Установка пишет только на выбранный носитель: папки, ELF (temp + rename), манифест, стартовые настройки по желанию и с сохранением чужих ключей. Карта памяти и конфиги лаунчеров не трогаются (BOOT-1): строки для FreeMcBoot и PS2BBL показываем.
  - Сеть только по действию пользователя или по включённой в настройках ежедневной проверке; перед загрузкой показываем лицензию и авторов; бинарники в сборку не входят (ADR-0007, ADR-0014).
  - Карточка есть у каждого подключённого носителя, но установка, обновление и замена предлагаются только носителям, которые подходят загрузчику: системный диск, том только для чтения и любой носитель с вердиктом «Не подходит для OPL» кнопок не получают, автоматическое окно обновления для них не показывается. «Установить…» на флешке с чужими файлами предлагает отформатировать её только через DEV-3 с защитами ADR-0013 (v0.2), а до этого — добавить OPL рядом с файлами или отформатировать вручную. Автоматическое окно «Доступно обновление» показывается при появлении носителя по кэшу каталога, без сети, один раз на пару «носитель, установленная сборка»; «Не сейчас» запоминается, кнопка на карточке открывает окно снова. Настройка «Предлагать обновления загрузчика автоматически» (по умолчанию включена) выключает окно целиком, и при запуске, и при появлении носителя; кнопки на карточке остаются.
  - POPStarter и Ember приходят только внутри пакета RiptOPL с релиза его автора (POPStarter без изменений как часть пакета, Ember по своей лицензии с файлом лицензии и ссылкой на Gageformer); отдельно они не скачиваются и не бандлятся. Файлы Sony (`POPS.ELF`, `IOPRP252.IMG`, BIOS) — никогда. Карточка устройства показывает состояние этих компонентов и точные пути недостающих файлов, а инструкции не пересказывает: каталог хранит ссылки на официальную документацию каждой сборки (README и wiki upstream, docs-сайт RiptOPL, POPSTARTERINFO), и интерфейс ведёт к ним (PS1-1).
  - YAOPL использует профиль OPL 1.2.0 beta: правила форматов совпадают, исправления форка касаются только того, что загрузчик терпит. Если форматы разойдутся, профиль разделим отдельным ADR.
- **Последствия.** В репозитории появляются каталог и история хешей как версионируемые данные, плюс workflow по расписанию (минуты CI: один запуск в сутки на Linux, ADR-0011). CI форка YAOPL должен публиковать `HASHES.txt` (задача в репозитории форка). LDR-1…LDR-4 для OPL и YAOPL делаются в M5 (v0.2) вместе с форматированием и мастером подготовки (DEV-3, DEV-4), форки — в M6; M4 остаётся обложками, метаданными и релизной сборкой, чтобы не перегружать веху.

## ADR-0023 — Профиль загрузчика определяется по носителю, настройка задаёт умолчание и переопределение
*2026-10-23, принято по запросу владельца продукта.* Уточняет LIB-1 и ADR-0022; правила — SPEC §5.1.1.
- **Контекст.** До M3 профиль был одной глобальной настройкой (по умолчанию OPL 1.2.0 beta), которая передавалась во все запросы. У владельца несколько носителей под разные загрузчики, и глобальный выбор легко забыть переключить: тогда на флешку под OPL 1.1.0 уедут ZSO и JPG-правила не той версии.
- **Решение.** Профиль вычисляется для каждого носителя по его файлам, без сети: установленный загрузчик (манифест, хеш) → файлы настроек и их ключи → косвенные признаки (exFAT, ZSO) → умолчание из настроек. Ответ `InspectDevice` несёт профиль, уровень уверенности и причину. Настройка «Профиль загрузчика» получает значение «Авто (по носителю)» как умолчание; явный выбор остаётся переопределением и может быть запомнен для носителя по серийному номеру тома. Интерфейс всегда показывает действующий профиль и почему он такой. Сканирование и планы получают действующий профиль, ядро само ничего не угадывает.
- **Последствия.** Ошибочное определение исправляется одним переопределением на носитель; неизвестный носитель ведёт себя как раньше (умолчание). Признаки совпадают с LDR-4, поэтому обе задачи делаются вместе в M5.
