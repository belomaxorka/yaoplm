# Журнал решений (ADR)

Формат: контекст → решение → последствия. Новые решения добавляются в конец. Отменённое решение не удаляется, а помечается `Заменено ADR-XXXX`.

## ADR-0001 — Стек: Tauri 2 + ядро на Rust + React/TS
*2026-10-22, принято.*
- **Контекст.** Нужны Windows, Linux и macOS, один код ядра для GUI, CLI и сервера, быстрая работа с многогигабайтными образами (research/04).
- **Решение.** Tauri 2.12 + Cargo workspace + axum + clap + React 19/TS/Vite.
  - Только в Rust есть поддерживаемые библиотеки без C-зависимостей для CHD, чтения и записи ISO, 7z, SMB2/3 и LZ4.
  - Сборки маленькие, есть официальный CI (`tauri-action`) и updater.
- **Отвергнуто.**
  - Wails v3 (Go): всё ещё beta, нет CHD, SMB-библиотека устарела. Пересмотреть после выхода v3.0.
  - Electron: инсталлятор 120–200 МБ, слабые нативные библиотеки.
  - Avalonia, Flutter, Qt: веб-интерфейс для сервера пришлось бы делать отдельно.
- **Последствия.** Высокий порог входа в Rust. Ядро держим синхронным, линтеры строгие, тестов много.

*2026-10-22, принято.*

  - GPL-2-only инструменты допустимо запускать только как отдельные процессы.

## ADR-0003 — Синхронное ядро, асинхронность только на краях
*2026-10-22, принято.* Крейты `core`, `formats`, `hash` и `device` не зависят от tokio, tauri и axum, что проверяется в CI. Так проще писать, тестировать и ревьюить код.

*2026-10-22, принято.*

- Профиль по умолчанию — 1.2.0 beta. Профили 1.1.0 и RiptOPL меняют правила (SPEC §4).

## ADR-0005 — Обложки всегда в PNG
*2026-10-22, принято.* OPL 1.2 beta читает только PNG (коммит c5a12a0), а 1.1.0 читает PNG, JPG и BMP. Значит, PNG подходит обоим. Размер ≤1024 px.

## ADR-0006 — Формат имени по умолчанию: `ID.Title.iso`
*2026-10-22, принято.* Если имя в старом формате (`SLUS_200.62.Title.iso`), OPL берёт ID из имени и не монтирует образ при сканировании: это быстрее и совместимо с 1.1.0. Формат `Title.iso` остаётся как опция.

## ADR-0007 — Политика источников данных
*2026-10-22, принято.*
- Приватный сервер обложек OPL Manager не используем: у него нет публичного API и условий использования.
- Изображения в сборку не включаем.
- Встраиваем только данные с совместимой лицензией (GameIndex — GPL-3.0, libretro-database — CC BY-SA 4.0) и указываем авторство.
- Источники без лицензии (xlenore/ps2-covers, compat-листы) используем только во время работы, по запросу пользователя, с кэшем.
- **Уточнение (2026-10-24, ADR-0035).** Резервные копии базы картинок, которые автор OPL Manager сам выложил на archive.org (`OPLM_ART_YYYY_MM`), — не частный сервер. Последняя из них читается по картинке на тех же условиях, что xlenore: по запросу, с кэшем, в сборку не входит.

## ADR-0012 — Защита API сервера
*2026-10-22, принято.* Уточняет ADR-0009.
- **Контекст.** Сервер на 127.0.0.1 без токена доступен любому сайту, открытому в браузере пользователя. Простой кросс-сайтовый POST (форма или `text/plain`) уходит без CORS-preflight, а DNS rebinding позволяет ещё и читать ответы. Начиная с M2, через API можно будет менять и удалять файлы.
- **Решение.** Для `/api/*`:
  - `POST /api/rpc` принимает только `Content-Type: application/json`. Кросс-сайтовый запрос с таким типом требует preflight, а мы его не обслуживаем.
  - Если пришёл заголовок `Origin`, он должен совпадать с `Host`.
  - Сервер на loopback **без токена** принимает только loopback-`Host` (`localhost`, `127.x.x.x`, `[::1]`). С токеном эта проверка не нужна: токен через DNS rebinding не подделать. Поэтому за reverse proxy сервер может слушать 127.0.0.1.
  - Токен передаётся в `Authorization: Bearer`. Только для WebSocket `/api/events` допускается `?token=`, потому что браузер не умеет слать заголовки при handshake.
  - UI получает токен один раз через адрес `/?token=…`: сохраняет его в localStorage и убирает из адресной строки.
  - Токен сравнивается за постоянное время.
- **Последствия.**
  - Reverse proxy должен передавать исходный `Host` (Caddy делает это по умолчанию, в nginx нужно `proxy_set_header Host $host`). Иначе `Origin` не совпадёт с `Host`.
  - Доступа к API с другого origin нет. Если понадобится, добавим явный allow-list.

## ADR-0013 — Форматирование съёмных носителей с защитой от ошибки
*2026-10-22, принято по запросу владельца продукта. Заменяет ADR-0008.*
- **Контекст.** Пользователю нужна подготовка носителя с нуля: флешка или SD-карта для MX4SIO и эмулятора карты памяти. Неправильная ФС, разметка или размер кластера — частая причина того, что OPL не видит игры или тормозит. Риски из ADR-0008 никуда не делись: ошибка уничтожает данные, а повышение прав в каждой ОС своё.
- **Решение.** Форматирование входит в продукт (SPEC DEV-3, DEV-4) с такими ограничениями:
  - Только съёмные диски на USB или SD-шине. Системный и загрузочный диск, а также диски с примонтированной ОС, недоступны вообще.
  - Перед планом показываем модель, серийный номер, размер, текущие разделы и метки томов.
  - Подтверждение вводом (например, метки или размера диска), а не одной кнопкой.
  - Прямо перед записью диск проверяется ещё раз по тому же идентификатору: если он сменился или переподключился, операция отменяется.
  - Запись выполняет отдельный процесс-помощник с повышенными правами (`yaoplm helper --stdio`), а не основной процесс.
  - Параметры (ФС, MBR/GPT, кластер, выравнивание) берутся из профиля носителя и загрузчика, пользователь может их изменить.
  - В автотестах форматируем только файлы-образы, никогда реальные диски.
- **Последствия.** Появляется самая опасная операция в продукте, поэтому её код отдельно ревьюит владелец и проверяет на своих носителях. Этап — v0.2: до этого остаётся диагностика носителя только на чтение (DEV-2).
- **Уточнение по research/06 (2026-10-22).**
  - Доступ к диску: повышенные права нужны только на Windows (помощник через UAC и защищённый именованный канал). На Linux непривилегированный помощник получает дескриптор устройства через udisks2 (один запрос polkit), на macOS — через `authopen` (нужен прототип). В режиме сервера и в Docker форматирования нет.
  - Подтверждение вводом — размер диска.
  - Сначала пишем файловую систему, таблицу разделов — последней; идентичность диска проверяем через тот же дескриптор, которым пишем.
  - Только диски с логическим сектором 512 байт: FatFs в OPL собран с `FF_MAX_SS 512` (проверено в `fjtrujy/FatFs` ветка `iop-r0.16`).
  - Выбор движка (свой exFAT или системный на Windows и macOS) зависит от вопроса о патентах exFAT — SPEC, открытый вопрос 6.

## ADR-0014 — Установка загрузчиков только с официальных релизов
*2026-10-22, принято.* Дополняет ADR-0007.
- **Контекст.** Владелец хочет ставить из программы разные сборки: официальный OPL, RiptOPL, форк с MMCE и другие (SPEC LDR-1…5). Бинарники PS2-программ меняются часто, у них разные лицензии.
- **Решение.**
  - Скачиваем только с официальных релизов проектов (GitHub Releases и аналоги), по явному действию пользователя. В сборку YAOPLM бинарники загрузчиков не входят.
  - Фиксируем сборку по SHA-256 ассета, а не по тегу: «плавающие» теги вроде `latest` перезаписываются на месте. Хеш берём из GitHub API, если релиз его публикует, иначе считаем и показываем свой. Кэшируем, показываем лицензию и ссылку на исходники.
  - Конфиги способов запуска (FreeMcBoot, PS2BBL) не пишем, а показываем пользователю строки для них (SPEC BOOT-1).
  - Можно установить из своего архива без сети.
  - Эксплойты (FreeMcBoot, PS2BBL) на физическую карту памяти не ставим.
- **Последствия.** Каталог загрузчиков — данные, которые обновляются без выпуска новой версии программы. Когда меняется формат релизов какого-то проекта, достаточно поправить его запись в каталоге.

## ADR-0015 — Эталонные проекты как источник граничных случаев
*2026-10-22, принято.*
- **Контекст.** В исходниках OPL, его форков и соседних программ годами копились исправления для особых случаев, ошибок железа и прошивок. Многие из них нигде не описаны, кроме комментариев в коде, коммитов и issues. Искать их по форумам долго.
- **Решение.**
  - Ведём справочник репозиториев `docs/research/REFERENCES.md` и их локальные клоны в `D:\yaoplm-testdata\refs\<owner>__<repo>`.
  - Перед реализацией формата или работы с устройством читаем соответствующий код в официальном OPL и форках, их коммиты и issues; при необходимости — ветки форумов (psx-place читаем через Chrome пользователя).
  - Сравниваем реализации. Эталон поведения — официальный OPL (CLAUDE.md: «Follow OPL source»); форки и другие менеджеры — источник граничных случаев и исправлений, которые проверяем, прежде чем переносить. В комментарии к нашему коду указываем файл и коммит источника.
  - Лицензии: код OPL (AFL-3.0) и ps2sdk (AFL-2.0) не копируем, а переписываем по смыслу (ADR-0002). Код под GPL-3-совместимыми лицензиями можно переносить с указанием авторства.
- **Последствия.** Справочник нужно поддерживать в актуальном состоянии (`git pull` по клонам), а находки — записывать в research/.

## ADR-0016 — Свой ридер ISO9660 и генератор фикстур вместо hadris-iso
*2026-10-22, принято в M1.* Уточняет стек в ARCHITECTURE.md §2.
- **Контекст.** ID игры должен совпадать с тем, что покажет OPL (IMP-2). isofs в OPL намного строже стандарта: читает только сектор 16, ищет в корне ровно `SYSTEM.CNF;1` через `strcmp` (с учётом регистра, версии `;1` и байта-заполнителя), обрабатывает записи нулевой длины по-своему (research/08 §3). Универсальная библиотека находит файл там, где OPL его не видит, и скрывает от нас причину. Для тестов нужны «неправильные» образы (без `;1`, с именем в нижнем регистре, со вторым PVD для DVD-9, больше 4 ГиБ без места на диске), а стандартные писатели такие не делают.
- **Решение.**
  - `yaoplm-formats::iso9660` — свой минимальный ридер, повторяющий логику isofs OPL (PVD, поиск в корне, чтение файла, проба слоя DVD-9), плюс простой стандартный листинг каталогов для отображения.
  - `yaoplm-test-support::iso` — свой генератор ISO9660 (PVD, терминатор, таблицы путей, каталоги, файлы), отдающий образ потоково через `Read + Seek`.
  - `hadris-iso` пока не подключаем. Вернёмся к нему, если понадобится полноценная запись ISO (например, BIN/CUE → ISO в IMP-1 можно сделать и без неё: это копирование секторов данных).
- **Последствия.** Около 600 строк своего кода, зато каждое правило покрыто тестом и fuzz-целью. ZSO-ридер встроен в тот же интерфейс `SectorSource`, поэтому все проверки работают одинаково для ISO, ZSO и цепочки чанков `ul`.

## ADR-0017 — Ветки вех вливаются обычным merge-коммитом
*2026-10-22, принято по предложению владельца продукта.*
- **Контекст.** PR вех (M0, M1…) содержат десятки осмысленных коммитов с ID требований. При squash история схлопывается в один коммит: теряются `git blame` по конкретному правилу и `git bisect` до коммита.
- **Решение.** PR вех и крупных задач вливаются через «Create a merge commit». Маленькие PR из одного логического изменения (например, только документы) можно вливать squash.
- **Последствия.** Каждый коммит в ветке должен собираться и проходить тесты сам по себе. Мелкие исправления («fix typo», правки clippy) агент вливает в исходные коммиты до открытия PR (`git commit --fixup` + `git rebase --autosquash`). Короткую историю по PR даёт `git log --first-parent main`.

## ADR-0018 — Свой форк OPL для исправления найденных багов
*2026-10-22, принято по решению владельца продукта.*
- **Контекст.** В M1 нашлись баги OPL на «кривых» входных данных (research/08 §10). Три из них не исправлены ни в upstream, ни в одном форке: чит с пустым именем из комментария с отступом, зависание на записи каталога ISO с пустым именем, деление на ноль в ZSO при `align > 11`. Ещё пять исправлены только в RiptOPL. Upstream развивается медленно, хотя PR сообщества принимает.
- **Решение.**
  - Форк `ps2homebrew/Open-PS2-Loader` под аккаунтом владельца, отдельный репозиторий. Лицензия форка — AFL-3.0, как у OPL. Код YAOPLM (GPL-3) в форк не копируем, код форка в YAOPLM — тоже нет (ADR-0002).
  - Своя линия развития: исправления коммитим прямо в форк, а не готовим как PR в upstream. Изменения upstream периодически подтягиваем в форк. Отправка отдельных исправлений в upstream возможна, но не обязательна и только с одобрения владельца.
  - Автоматическая сборка в GitHub Actions форка на каждый пуш в основную ветку, с публикацией готового ELF (по образцу rolling-релиза `latest` в upstream), чтобы владелец ставил наш OPL с исправлениями на консоль.
  - Исправления RiptOPL переносим выборочно: только реальные баги и только после проверки «до/после» на воспроизводящих входных данных. Авторство указываем (та же лицензия AFL-3.0).
  - Проверка — на консоли владельца и на фикстурах `yaoplm-test-support`; чисто логические функции (разбор CHT, `SYSTEM.CNF`, `ul.cfg`) дополнительно проверяем, собирая их на PC в тестовом стенде.
  - Как только форк начнёт выпускать сборки, добавим в YAOPLM профиль загрузчика для него (правила форматов пока совпадают с upstream).
- **Последствия.** Появляется второй репозиторий со своим циклом и обязанность подтягивать upstream. YAOPLM по-прежнему не полагается на исправления: менеджер не создаёт «кривые» данные и предупреждает о них при сканировании, потому что у пользователей может стоять любой загрузчик.

## ADR-0019 — Тома и предвыделение через API ОС, `unsafe` только в одном модуле
*2026-10-22, принято в M2.* Уточняет стек в ARCHITECTURE.md §2 и §8.
- **Контекст.** Для DEV-1/DEV-2 и для повторной проверки носителя перед записью нужны серийный номер тома, размер кластера и сектора, шина (USB/SD), таблица разделов и смещение раздела, а для записи (IMP-7) — предвыделение места. `sysinfo` даёт только точку монтирования, тип ФС, объём и признак «removable» (на Windows это `GetDriveTypeW`, а USB-диски там «fixed»), не видит сетевые диски и не умеет «том по пути». Ни один из найденных крейтов не закрывает всё сразу.
- **Решение.**
  - `yaoplm-device` обращается к ОС напрямую:
    - Windows — `windows-sys` 0.61: `GetVolumeInformationW`, `GetDiskFreeSpace(Ex)W`, `GetVolumePathNameW`, `IOCTL_STORAGE_QUERY_PROPERTY` и `IOCTL_DISK_GET_PARTITION_INFO_EX` на дескрипторе тома с доступом 0 (без прав администратора), предвыделение — `SetFileInformationByHandle(FileAllocationInfo)`;
    - Linux — `/proc/self/mountinfo`, sysfs, `/dev/disk/by-uuid` и `by-label`, `statvfs` и `fallocate(FALLOC_FL_KEEP_SIZE)` через `rustix` 1.1;
    - macOS — `statfs` через `rustix` и `/Volumes`; шина, раздел и серийный номер пока не определяются, предвыделения нет (`F_PREALLOCATE` в rustix ещё и удлиняет файл, а msdosfs заполняет удлинение нулями).
  - `sysinfo` не подключаем.
  - `unsafe` в workspace по-прежнему запрещён (`unsafe_code = "deny"`). Единственное исключение — `crates/yaoplm-device/src/sys/windows.rs`: тонкие обёртки над документированными вызовами Win32, буферы выделяет Rust, у каждого блока комментарий `SAFETY`. *Уточнение ADR-0037:* так же устроены `sys/fiemap.rs` (Linux) и `sys/log2phys.rs` (macOS) для подсчёта кусков файла.
- **Последствия.** Около 300 строк платформенного кода, который CI проверяет на трёх ОС. Подробности для macOS (DiskArbitration или `diskutil`) — позже, вместе с DEV-3.

## ADR-0020 — Переименование меняет то, что OPL связывает с названием; VMC не трогаем никогда
*2026-10-23, принято в M2.* Уточняет SPEC GAME-1 и GAME-2.
- **Контекст.** GAME-1 требовал «синхронно обновлять ART, CFG, CHT и ссылки на VMC» при переименовании. Но OPL называет CFG, ART и CHT по ID игры, а не по названию, и ни OPL, ни его форки, ни соседние менеджеры при смене названия их не трогают (research/09 §4). Карты VMC OPL по умолчанию называет `<ID группы или ID>_<слот>`, есть ещё `generic_0`/`generic_1`: одна карта часто общая для серии игр.
- **Решение.**
  - Новое название меняет только имя образа или, для `ul`, имена чанков (их хеш считается от названия) и запись `ul.cfg`; `games.bin` в папке удаляется.
  - CFG (и `.info` wOPL), `ART/<ID>_*` и `CHT/<ID>.cht` переносятся только когда меняется действующий ID: пользователь исправил ID в имени старого формата или в записи `ul.cfg`, либо смена формата имени меняет ID, который возьмёт OPL. Если старый ID есть ещё у другой игры, файлы копируются, а не переносятся. Существующий файл с новым именем останавливает план.
  - Файлы VMC и значения `$VMC_0`/`$VMC_1` не меняются никогда: CFG переезжает целиком и продолжает указывать на ту же карту. Так «ссылки на VMC» сохраняются, а общие карты не ломаются.
  - Удаление по умолчанию стирает только образ (или запись `ul.cfg` и чанки). CFG, обложки и читы — по явному выбору и только если ID не использует другая игра; VMC не удаляется никогда.
  - Каждый CFG перед переносом или удалением копируется в `.yaoplm/backup/<id>/` (CFG-5).
- **Последствия.** Переименование не может испортить настройки другой игры. Удаление сейвов VMC — отдельная функция с отдельным подтверждением (VMC-2, later).

## ADR-0021 — Транзакции с точкой фиксации и журнал на устройстве
*2026-10-23, принято в M2.* Уточняет ARCHITECTURE.md §5.
- **Контекст.** SPEC требует атомарной записи и журнала многошаговых операций с откатом или докатом. Флешку могут выдернуть посреди нарезки 8 ГБ; ни один из изученных менеджеров не переживает такой сбой без мусора на носителе (research/09 §1, §5).
- **Решение.**
  - План — список транзакций (одна игра, одно переименование…), транзакция — список шагов с точкой фиксации. Шаги до неё обратимы. Шаг прямо перед ней делает изменение видимым для OPL: переименование образа на место или запись `ul.cfg`. Шаги после неё только завершают работу: удаление `games.bin`, удаление по просьбе пользователя, удаление источника при переносе.
  - Журнал — JSON в `.yaoplm/journal/<id>.json` в корне устройства: весь план и число выполненных шагов каждой транзакции. Перезаписывается атомарно после каждого шага и удаляется, когда план завершён. OPL корень не показывает, NHDDL пропускает имена с точкой.
  - Сбой или отмена до точки фиксации откатывает транзакцию (новые шаги первыми); после неё журнал остаётся, и восстановление докатывает транзакцию. Незафиксированную транзакцию по выбору пользователя можно не откатить, а повторить. Шаги восстановления идемпотентны, поэтому прерванное восстановление можно запустить снова.
  - Перед первой записью исполнитель повторно проверяет отпечаток тома (серийный номер, ФС, размер, метка), неизменность источников (размер и время изменения), свободное место и отсутствие незавершённых журналов.
  - Планы хранятся на стороне ядра (`PlanStore`); клиент отправляет только id плана. План выполняется один раз и живёт час. План с удалением пользовательских файлов требует явного `confirmDelete`.
  - Задания записи выполняются строго по одному в порядке очереди: параллельная запись на одну флешку фрагментирует обе игры.
- **Последствия.** На носителе появляется папка `.yaoplm` (журналы и резервные копии CFG). Пакет из N игр — N независимых транзакций: сбой на третьей игре оставляет первые две на месте.

## ADR-0022 — Каталог загрузчиков, идентичность сборки по хешу и обновление только в пределах канала
*2026-10-23, принято по запросу владельца продукта.* Уточняет ADR-0014 и ADR-0018; детали — SPEC §5.10.1, источники — research/07.
- **Контекст.** Владелец хочет режим установки загрузчика на носитель (папки по профилю плюс ELF по способу запуска) и обновление: программа определяет, какой загрузчик и какой версии стоит на флешке, и предлагает свежую сборку того же форка, а не другой. Сложности: ELF упакован ps2-packer, версии внутри не видно; плавающие теги (`latest`, `rolling`) перезаписывают ассеты; `digest` GitHub есть только у недавно загруженных файлов; из репозиториев мы контролируем только свой форк YAOPL.
- **Решение.**
  - Каталог сборок — данные в `data/loaders/`, а не код: семейство, канал, репозиторий, лицензия, профиль, ассеты, набор папок, пресеты путей, отпечатки. Обновляется без выпуска новой версии программы.
  - Идентичность сборки — семейство + канал + версия + SHA-256 ELF. История хешей ведётся только дописыванием: для YAOPL — `HASHES.txt`, который дописывает CI форка; для чужих репозиториев — `data/loader-hashes/<id>.txt` у нас, которые раз в сутки дополняет workflow по расписанию из GitHub Releases API; всё скачанное самим YAOPLM запоминается в локальном кэше. Неизвестный хеш — нормальный случай: такая сборка показывается как «семейство X, версия неизвестна».
  - Распознавание по порядку: манифест установки `.yaoplm/manifest.json` → история хешей → `title.cfg` → имена файлов → отпечатки файлов настроек. Результат всегда сопровождается уровнем уверенности.
  - Обновление предлагается только в пределах того же семейства и канала; смена форка, канала или пути ELF — отдельное явное действие «Заменить». Обновление меняет только ELF (и пакет приложения у RiptOPL), держит резервную копию прежнего ELF и умеет откатиться.
  - Установка пишет только на выбранный носитель: папки, ELF (temp + rename), манифест, стартовые настройки по желанию и с сохранением чужих ключей. Карта памяти и конфиги лаунчеров не трогаются (BOOT-1): строки для FreeMcBoot и PS2BBL показываем.
  - Сеть только по действию пользователя или по включённой в настройках ежедневной проверке; перед загрузкой показываем лицензию и авторов; бинарники в сборку не входят (ADR-0007, ADR-0014).
  - Карточка есть у каждого подключённого носителя, но установка, обновление и замена предлагаются только носителям, которые подходят загрузчику: системный диск, том только для чтения и любой носитель с вердиктом «Не подходит для OPL» кнопок не получают, автоматическое окно обновления для них не показывается. «Установить…» на флешке с чужими файлами предлагает отформатировать её только через DEV-3 с защитами ADR-0013 (v0.2), а до этого — добавить OPL рядом с файлами или отформатировать вручную. Автоматическое окно «Доступно обновление» показывается при появлении носителя по кэшу каталога, без сети, один раз на пару «носитель, установленная сборка»; «Не сейчас» запоминается, кнопка на карточке открывает окно снова. Настройка «Предлагать обновления загрузчика автоматически» (по умолчанию включена) выключает окно целиком, и при запуске, и при появлении носителя; кнопки на карточке остаются.
  - POPStarter и Ember приходят только внутри пакета RiptOPL с релиза его автора (POPStarter без изменений как часть пакета, Ember по своей лицензии с файлом лицензии и ссылкой на Gageformer); отдельно они не скачиваются и не бандлятся. Файлы Sony (`POPS.ELF`, `IOPRP252.IMG`, BIOS) — никогда. Карточка устройства показывает состояние этих компонентов и точные пути недостающих файлов, а инструкции не пересказывает: каталог хранит ссылки на официальную документацию каждой сборки (README и wiki upstream, docs-сайт RiptOPL, POPSTARTERINFO), и интерфейс ведёт к ним (PS1-1).
  - YAOPL использует профиль OPL 1.2.0 beta: правила форматов совпадают, исправления форка касаются только того, что загрузчик терпит. Если форматы разойдутся, профиль разделим отдельным ADR.
- **Последствия.** В репозитории появляются каталог и история хешей как версионируемые данные, плюс workflow по расписанию (минуты CI: один запуск в сутки на Linux, ADR-0011). CI форка YAOPL должен публиковать `HASHES.txt` (задача в репозитории форка). LDR-1…LDR-4 для OPL и YAOPL делаются в M5 (v0.2) вместе с форматированием и мастером подготовки (DEV-3, DEV-4), форки — в M6; M4 остаётся обложками, метаданными и релизной сборкой, чтобы не перегружать веху.

## ADR-0023 — Профиль загрузчика определяется по носителю, настройка задаёт умолчание и переопределение
*2026-10-23, принято по запросу владельца продукта.* Уточняет LIB-1 и ADR-0022; правила — SPEC §5.1.1.
- **Контекст.** До M3 профиль был одной глобальной настройкой (по умолчанию OPL 1.2.0 beta), которая передавалась во все запросы. У владельца несколько носителей под разные загрузчики, и глобальный выбор легко забыть переключить: тогда на флешку под OPL 1.1.0 уедут ZSO и JPG-правила не той версии.
- **Решение.** Профиль вычисляется для каждого носителя по его файлам, без сети: установленный загрузчик (манифест, хеш) → файлы настроек и их ключи → косвенные признаки (exFAT, ZSO) → умолчание из настроек. Ответ `InspectDevice` несёт профиль, уровень уверенности и причину. Настройка «Профиль загрузчика» получает значение «Авто (по носителю)» как умолчание; явный выбор остаётся переопределением и может быть запомнен для носителя по серийному номеру тома. Интерфейс всегда показывает действующий профиль и почему он такой. Сканирование и планы получают действующий профиль, ядро само ничего не угадывает.
- *Уточнение ADR-0040:* глобальной настройки профиля больше нет; действуют выбор для носителя и определение по его файлам.
- **Последствия.** Ошибочное определение исправляется одним переопределением на носитель; неизвестный носитель ведёт себя как раньше (умолчание). Признаки совпадают с LDR-4, поэтому обе задачи делаются вместе в M5.

## ADR-0024 — Встроенная база названий: сжатый JSON внутри бинарника
*2026-10-23, принято в M4.* Уточняет ARCHITECTURE.md §6-§7 и SPEC META-1.
- **Контекст.** Нужна база «серийный номер → название, регион, родственные серийники, имена Redump» из PCSX2 `GameIndex.yaml` (GPL-3.0) и libretro-database PS2 DAT (CC BY-SA 4.0). Имена Redump нужны ещё и для libretro-thumbnails: файлы там названы по Redump. Варианты: SQLite-файл рядом с бинарником или сжатый JSON внутри него.
- **Решение.** `scripts/build-data.py` собирает `data/titles.json.gz` (12 978 серийников, 377 КБ, gzip с нулевым mtime: одинаковый вход даёт одинаковые байты) и `data/ATTRIBUTION.md` из `data/attribution.json` с SHA-256 входных файлов. `yaoplm-core::titles` встраивает файл через `include_bytes!` и разбирает при первом обращении (`OnceLock`, несколько миллисекунд, около 3 МБ в памяти). ID принимаются в обоих написаниях (`SLUS_200.62`, `SLUS-20062`, суффиксы регионов отбрасываются; `yaoplm_formats::serial`). Для японских названий предпочитается `name-en`.
- **Отвергнуто.** SQLite: тянет компиляцию C-кода в ядро, требует файл на диске рядом с каждым из трёх интерфейсов (и в Docker), а запросов сложнее «найти по ключу» у нас нет. Загрузка базы из сети при первом запуске: противоречит офлайн-первому подходу и ADR-0007.
- **Последствия.** Обновление базы — пересборка скриптом и коммит (`python scripts/build-data.py`), файл помечен `binary` в `.gitattributes`. Производная база остаётся под CC BY-SA 4.0 в части libretro и распространяется с программой под GPL-3.0-or-later.

## ADR-0025 — Обложки: поиск как задание, запись как план, резервная копия переносом
*2026-10-23, принято в M4.* Уточняет ARCHITECTURE.md §5-§7, SPEC ART-1…ART-4, ADR-0021.
- **Контекст.** Массовая загрузка обложек для сотен игр идёт минутами (не чаще одного запроса в секунду на источник, ADR-0007), а синхронный запрос плана этого не выдержит: без прогресса, без отмены. При этом запись на носитель обязана остаться планом с подтверждением (правило 1). Существующую обложку при замене нельзя просто удалить: удаление пользовательских файлов требует отдельного подтверждения, а журнал не должен носить в себе байты картинок.
- **Решение.**
  - `FetchArt` — задание: сканирует носитель, для каждой игры в охвате (`missing` по умолчанию или `all`) спрашивает `yaoplm-net`, пишет строку журнала на игру (найдено, из кэша, не найдено, ошибка) и завершается планом `PlanKind::Art`, который пользователь подтверждает как любой другой. `SetArt` (файл, drag-and-drop, буфер обмена) и `DeleteArt` возвращают план сразу.
  - Источники: xlenore/ps2-covers по серийнику, затем libretro-thumbnails по имени Redump из встроенной базы (ADR-0024), сначала `thumbnails.libretro.com`, затем raw GitHub. Никакого GitHub API. У каждого источника есть режим локального зеркала (папка с раскладкой репозитория), он же мок для тестов и e2e. Настройки источников и зеркала приходят с запросом от интерфейса; на сервере зеркало должно лежать внутри разрешённых корней.
  - Кэш: `art-cache/<source>/<key>/original.<ext>` плюс производные `COV-<w>x<h>.png`, манифест `cache.sqlite`; «не найдено» помнится семь дней; `ETag`/`Last-Modified` для условных запросов; каталог данных — `YAOPLM_DATA_DIR` или системная папка приложения (`--data-dir` у сервера). Кэш можно удалить без потерь.
  - Перекодирование: любой PNG/JPEG/BMP/GIF/WebP → PNG 8 бит на канал, размер COV из профиля (140×200 для OPL, 280×400 для RiptOPL), растяжение без обрезки, как делает сам OPL (ADR-0005).
  - План записи: одна транзакция на игру, источник шага `WriteFile` — файл в кэше на хосте, так что журнал хранит только путь. Существующий файл `ART/<ID>_COV.*` переносится (`Rename`) в `.yaoplm/backup/<id>/ART/` до точки фиксации: откат возвращает его на место, удаления нет. `DeleteArt` копирует файл туда же и удаляет после точки фиксации, что требует `confirmDelete`.
  - Показ: на десктопе через asset-протокол Tauri с разрешением только на `<корень>/ART` во время работы; на сервере `GET /media/art?path=` только для файлов `ART/<ID>_<SUFFIX>.png|jpg|bmp` внутри корней, с `ETag` и `?token=` как у потока событий.
- **Последствия.** В M4 только COV; остальные типы (ICO, SCR, BG…) добавляются как новые `ArtKind` в том же конвейере (v0.2). Сеть используется только внутри `FetchArt`, по действию пользователя. На носителе появляется `.yaoplm/backup/<id>/ART/` после замены или удаления обложки.
- **Уточнение (2026-10-23, по решению владельца продукта).** Разделение «импорт, потом отдельная кнопка» временное. В v0.2 поиск обложек встраивается в импорт (SPEC ART-8, §5.4.1): галочка на экране добавления запускает то же задание `FetchArt` по ID образов из плана, а план импорта перестраивается с его результатом, так что образ и обложка пишутся одним подтверждённым планом. Сам конвейер (задание с журналом → план с файлами из кэша → резервная копия переносом) не меняется; меняется только то, что план импорта умеет принимать готовые обложки. Обложка никогда не блокирует импорт. Отдельная кнопка «Скачать обложки» остаётся для уже импортированных игр. Редактирование по типам (COV, ICO, COV2, BG, SCR, SCR2, LGO, LAB) в карточке игры — часть ART-2/ART-3 в v0.2.

## ADR-0026 — Проверка дампов: DAT Redump по кнопке, свой недельный лимит, вердикты из кэша хешей
*2026-10-23, принято в M5.* Уточняет SPEC GAME-5 и META-2, ARCHITECTURE.md §6.
- **Контекст.** `https://redump.info/datfile/ps2/serial,version` отдаёт zip с одним Logiqx-DAT (около 1,3 МБ, 11 845 игр на 2026-10-23), но без `ETag` и `Last-Modified`: условные запросы из META-2 ничего не экономят. Redump считает хеши CD по сырым дорожкам BIN (2352 байта на сектор), поэтому ISO, снятый с CD, не совпадёт никогда. Чтение образа на 4 ГБ с флешки идёт минутами, а библиотеку сканируют постоянно.
- **Решение.**
  - DAT хранится в каталоге данных приложения (`db/redump-ps2.dat`, метаданные `db/redump-ps2.json`). Redump спрашивают только по кнопке «Скачать» или «Проверить обновление» и не чаще раза в неделю, причём считается любой ответ сервера, включая страницу ошибки (`db/redump-ps2.asked`); отсутствие ответа (нет сети) не считается. Обновления и импорт идут по одному. Вместо загрузки можно импортировать скачанный вручную `.dat` или `.zip` без сети. Файлы пишутся через временный файл, `fsync` и переименование; повреждённые метаданные восстанавливаются из DAT, неразборчивый DAT считается отсутствующим.
  - Хеши CRC-32 и SHA-1 (MD5 по желанию) считаются за одно чтение образа: ISO как есть, ZSO распакованным, `ul` склеенным из частей. Совпадение — по SHA-1 и размеру; при нескольких совпадениях выигрывает запись с ID игры.
  - Статусы: «проверен», «плохой дамп» (ID есть в Redump, хешей нет), «неизвестен» с причиной (нет DAT; нет в Redump; образ CD — с записями того же ID и подсказкой «тот же размер»), «ошибка проверки» (образ не читается).
  - Хеши кэшируются в `cache.sqlite` по ключу «том (серийный номер, ФС, размер) + путь + размер + время изменения» каждого файла. Сканирование показывает вердикт только из кэша (открывает его только на чтение и ничего не создаёт), против текущего DAT. Опция «Перечитать заново» (`fresh`) игнорирует кэш.
- **Последствия.** Проверка никогда не пишет на носитель. Новый DAT меняет вердикты без перечитывания образов. ISO с CD получают «неизвестен: образ CD» вместо ложного «плохой дамп». Без DAT проверка всё равно считает и кэширует хеши.

## ADR-0027 — Конвертации ISO ↔ ZSO ↔ ul и уточнение восстановления
*2026-10-23, принято в M5.* Уточняет SPEC GAME-4 и ADR-0021.
- **Контекст.** Конвертация удаляет исходный образ, а свободного места на флешке часто впритык. Размер ZSO заранее неизвестен. Записи `ul.cfg` с одинаковыми названием и ID указывают на одни и те же части (имена частей — CRC названия и ID, `sbCreatePath_name()`), а OPL при удалении (`sbDelete()`) убирает только одну запись. Ревью нашло, что прерванное восстановление с шагом, который падает каждый раз (ZSO больше 4 ГБ на FAT32), повторялось бы бесконечно.
- **Решение.**
  - Одна транзакция на игру во всех направлениях (ISO, ZSO, ul в любую сторону). Новая форма пишется рядом со старой; старая удаляется после точки фиксации и только с `confirmDelete`. ID игры не меняется: CFG, картинки, читы и VMC продолжают работать. Если при именах «только название» ID в `ul.cfg` отличается от SYSTEM.CNF, ID остаётся в имени файла.
  - Место считается по пику (новый файл до удаления старого), ZSO — по худшему случаю, с округлением до кластера на каждый файл.
  - Из `ul.cfg` удаляются все записи этой игры (отступление от `sbDelete()`, research/12 §3). Части, размер которых OPL прочитал бы иначе (все, кроме последней, ровно 1 ГиБ), не склеиваются.
  - Откат и докат шага ZSO трогают файл, только если его заголовок говорит, что это ZSO этого источника.
  - Уточнение ADR-0021: транзакции восстановления сохраняют исходную точку фиксации (незафиксированная часть остаётся обратимой), а план восстановления после отката одной транзакции продолжает остальные и закрывает журналы. Шаг, который не может выполниться, откатывается один раз, а не повторяется при каждом восстановлении.
- **Последствия.** На FAT32 конвертация в ZSO образа почти в 4 ГБ может откатиться, если ZSO выйдет больше 4 ГБ (план предупреждает). После неудачного «Продолжить» в восстановлении игра остаётся в прежнем виде.

## ADR-0028 — Источники в архивах, CHD и многодорожечные BIN/CUE
*2026-10-23, принято в M5.* Уточняет SPEC IMP-1b.
- **Контекст.** Игры часто скачивают в zip и 7z. Распаковка во временную папку (как у Orbit) удваивает место и время. CHD хранит карту блоков в конце файла, и блоки ссылаются назад. Диски PS2 с CD-аудио после дорожки данных существуют, но OPL запускает только диски с одной дорожкой. Декодер RAR (`unrar`) несовместим с GPL-3 по лицензии.
- **Решение.**
  - Архив zip или 7z читается как папка (`ArchiveSources`); образ распаковывается на лету и сразу пишется на носитель, без временных файлов. Имена членов архива очищаются, как это делает 7-Zip (без букв дисков, `.` и `..`), поэтому член архива не может выйти за его пределы. CRC каждого члена проверяется при чтении до конца.
  - Архивы никогда не удаляются, даже в режиме переноса (план об этом пишет). Архив внутри архива не открывается. CHD внутри архива не читается (его нужно сначала извлечь). Архивы с паролем отклоняются. RAR остаётся в IMP-1c за отдельной опцией сборки.
  - CHD: DVD и CD (`CHT2`), сохранённый pregap, все режимы данных; CHD, которому нужен родительский CHD, отклоняется сразу.
  - BIN/CUE: данные — дорожка 1. Звуковые дорожки после неё отбрасываются с предупреждением. Вторая дорожка данных или вторая сессия отклоняются. Поддерживаются и файлы Redump по одному на дорожку, и один BIN со всеми дорожками.
- **Последствия.** Импорт из solid-7z с несколькими играми декодирует всё, что лежит перед нужной игрой. Музыка с CD-аудио в таких играх на PS2 не играет, как и при любой записи для OPL.

## ADR-0029 — Тексты ядра — фразы: ключ каталога и параметры
*2026-10-23, принято в M5.* Уточняет docs/I18N.md и ARCHITECTURE.md §4.
- **Контекст.** Интерфейс переведён на русский, но заголовки планов, транзакций и заданий и тексты ошибок ядро собирало английскими строками (`format!`), и русский интерфейс показывал «Import 2 games». Если держать английские шаблоны и в Rust, и в каталоге интерфейса, они рано или поздно разойдутся.
- **Решение.**
  - Тип `Phrase { key, params }` в `yaoplm-core`: ключ каталога (`titles.*`, `errors.*`, `notices.*`) и именованные параметры. Параметр — число (количество выбирает форму множественного числа; размер в байтах пишется как `{{size, bytes}}`), текст (имя, путь, ID, формат) или вложенная фраза.
  - Английский текст ядро берёт из того же каталога `web/src/locales/en/translation.json`: он встроен через `include_str!`, как `data/titles.json.gz` (ADR-0024). CLI, логи и английский интерфейс говорят одно и то же. Ключ, которого нет в каталоге, — ошибка в отладочной сборке.
  - С фразой рядом с английским текстом идут заголовки планов и транзакций (`title_phrase`), заголовки и текущий элемент заданий, ошибки выполнения плана (`ExecError::phrase`), ошибки планирования (`OpError` хранит фразу) и ошибки API (`ApiError.phrase`). Журналы на носителе получают поле `title_phrase` с `serde(default)`: старые журналы читаются, их заголовки остаются английскими (ключ `titles.plan` передаёт текст как есть).
  - Интерфейс переводит фразу сам (`phraseText`, `errorText` в `web/src/lib/phrase.ts`): вложенные фразы — первыми; ключ, которого нет в каталоге (ядро новее интерфейса), показывает английский текст ядра.
  - Проверки: vitest находит ключи фраз в исходниках ядра и API и требует перевод во всех языках, а также не допускает ключей `titles.*`/`errors.*`, которые ядро не использует; тесты ядра и API сверяют английский текст с фразой.
- **Отвергнуто.** Английские шаблоны и в Rust, и в каталоге (разойдутся). Перевод на стороне ядра: ядро не знает язык интерфейса, а сервер обслуживает разных клиентов. gettext или Fluent: второй формат каталога рядом с i18next.
- **Последствия.** Новый текст для пользователя в ядре — это фраза и ключ во всех языках в том же коммите.
- **Уточнение (2026-10-23, второй шаг).** Фразами стали и уведомления планов, предупреждения игр, советы по носителю и причины пропуска (`notices.*`), а причины из разборщиков форматов — `reasons.*`, фрагменты для встраивания после двоеточия. Тип `Phrase` и английский рендер вынесены в крейт `yaoplm-i18n`, чтобы ими пользовался и `yaoplm-device`; `yaoplm-core` реэкспортирует их. `Notice` хранит фразу (в `Box`, рядом с кодом и английским `message`); заблокированный план вкладывает фразу блокирующего уведомления целиком, с размерами. Несколько кодов разделены так, чтобы у каждого был один текст (`allHaveCovers`, `sourceMissing`, `tooLargeUseUl`, `imageDeletedAfterUl`, `chunksDeletedAfterImage`, `relatedShared`, `zsoDecompressedForOpl110`/`ForUl`). Числа в интерфейсе форматируются по языку («5,0 ГиБ»). Граница перевода — docs/I18N.md, правило 8.

## ADR-0030 — Проверка дампов при добавлении: хеши в том же проходе, сырая дорожка CD, порядок вердиктов
*2026-10-23, принято в M5.* Уточняет SPEC GAME-5 и ADR-0026.
- **Контекст.** Владелец продукта решил, что игры проверяются при добавлении сами (по умолчанию включено). Отдельное чтение флешки после записи — самая медленная часть: запись образа на 4 ГБ и его повторное чтение удваивают время. Redump хеширует CD по сырым дорожкам BIN (2352 байта на сектор), а на носитель пишется ISO (2048 байт), так что вердикт «подтверждён» для CD возможен, только если хешировать сырую дорожку данных ещё в источнике.
- **Решение.**
  - Хеши считаются в том же потоке, что и запись (`yaoplm-core::checks`): CRC-32 на потоке записи, SHA-1 и MD5 в рабочих потоках (`StreamHasher`). Образ хешируется так, как его читает OPL: секторы ISO; ZSO, скопированный как есть, распаковывается на лету (`zso::StreamDecoder`); при записи в ZSO хешируются данные ISO до сжатия.
  - Для CD из BIN/CUE и CHD дополнительно хешируется сырая дорожка данных (`SectorSource::raw_sector`), сектор за сектором по мере декодирования. Звуковые дорожки в DAT общие у разных дисков, поэтому по сырому хешу сверяется только дорожка данных (первый `.bin` игры).
  - Хеши выходят, только если источник прошёл целиком с первого байта за один проход. Возобновлённая или упавшая запись хешей не даёт; такую игру проверяет обычный `VerifyGames`.
  - После записи хеши кладутся в кэш по ключу нового файла на носителе (том, путь, размер, mtime), как это сделал бы `VerifyGames`, а хеш дорожки — в таблицу `tracks` по паре «SHA-1 и размер образа». Скан библиотеки берёт вердикт из кэша и находит дорожку через эту связь, так что CD сохраняет «подтверждён по дорожке» и после пересканирования.
  - Такие строки кэша помечены как снятые при записи (`hashes.from_writing`): хеши взяты с байтов источника, а носитель после записи не перечитывается, и флешка с поддельным объёмом или сбоями, испортившая данные, иначе получила бы «подтверждён (из кэша)» без единого чтения. Скан библиотеки показывает вердикт и по помеченным строкам, а явная проверка дампов (`VerifyGames`) считает такую строку промахом: читает файлы с носителя один раз и сохраняет обычную строку. Строки из кэша до этой пометки считаются прочитанными с носителя.
  - Порядок вердикта: сырая дорожка подтверждена → по дорожке; иначе ISO подтверждён → по образу; иначе вердикт дорожки (он точнее для CD). `DumpCheck.byTrack` показывает, по чему вынесен вердикт.
  - Переключатель «Проверять дампы при добавлении» на экране добавления (по умолчанию включено, `PlanImport.verify`; с ADR-0034 его нет в настройках); в CLI проверка тоже идёт по умолчанию, `yaoplm add --no-verify` её выключает. Без DAT хеши всё равно сохраняются: вердикт появится, когда DAT будет загружен.
- **Последствия.** Проверка при добавлении не читает носитель повторно и почти не замедляет запись (SHA-1 в отдельном потоке; `opt-level = 3` для `sha1`, `md-5` и `crc32fast` в dev-профиле, чтобы отладочные сборки не тормозили). На FAT32 смена летнего времени сдвигает mtime и ключ кэша; вердикт CD тогда восстанавливается повторным хешированием и связью в `tracks`. Риск: сектора Mode 2 Form 2 в постгэпе реальных CD; нужна проверка на настоящем дампе Redump (research/13 §6).

## ADR-0031 — Обложки и названия при добавлении игр: набор обложек вместо плана
*2026-10-23, принято в M5.* Уточняет SPEC ART-8 (§5.4.1), META-1 и уточнение ADR-0025.
- **Контекст.** Обложки должны ложиться вместе с играми одним подтверждением, а поиск идёт минутами и может ничего не найти. Если бы поиск возвращал план, его пришлось бы сливать с планом импорта. Владелец продукта также попросил подставлять название из базы, когда ID известен, чтобы добавление было максимально простым.
- **Решение.**
  - `FetchArt` с `import: <id плана импорта>` ищет обложки для ID из этого плана (каждый ID один раз, без тех, у кого обложка на носителе уже есть) и заканчивается не планом, а набором обложек (`JobResult::Covers`: найденные `ArtItem` из кэша и причины для ненайденных). Набор хранится в `PlanStore` до часа, как план.
  - `PlanImport` с `covers: <id набора>` перестраивает план: за транзакцией игры идёт транзакция записи `ART/<ID>_COV.png`; ненайденные попадают в «пропущено»; дубликаты ID получают одну обложку. Обложка никогда не блокирует импорт.
  - Интерфейс запускает поиск после первого плана, показывает журнал под планом и блокирует «Подтвердить», пока план перестраивается; отмена поиска оставляет план без обложек. Галочка «Скачивать обложки для добавляемых игр» включена по умолчанию и запоминается (с ADR-0034 — «Скачивать картинки», все типы источников, только на экране добавления). В CLI — `yaoplm add --covers` (сеть только по флагу, ADR-0007), с `--mirror` и `--skip-source`.
  - Названия из базы: `PlanImport.databaseTitles` даёт игре название из встроенной базы (ADR-0024), если ID там есть, иначе название из имени файла. Переключатель «Названия из базы» на экране добавления включён по умолчанию; в CLI — `--db-titles`, по умолчанию выключено, чтобы скрипты получали предсказуемые имена. Название, отличное от имени файла, отмечается уведомлением в плане.
- **Отвергнуто.** Слияние двух планов на клиенте: план — контракт ядра, клиент его не правит. Поиск обложек внутри `PlanImport`: план должен строиться за секунды и без сети.
- **Последствия.** Кнопка «Скачать картинки» в библиотеке остаётся для игр, добавленных раньше. Набор обложек старше часа отклоняется (`coversExpired`): интерфейс оставляет план на экране, перестраивает его без обложек и запускает поиск заново.

## ADR-0032 — Типы картинок: источники по типам, ключи кэша, логотип вписывается, варианты на выбор
*2026-10-23, принято в M5.* Уточняет SPEC ART-2, ART-3 и ADR-0025.
- **Контекст.** OPL читает восемь типов картинок (research/13 §1), а открытые источники есть не для всех. Размеры у типов разные, а логотипы libretro бывают любой пропорции.
- **Решение.**
  - `ArtKind` и тип протокола `ArtType`: COV, ICO, COV2, BG, SCR, SCR2, LGO, LAB; размеры — `recommended_size` по профилю (ICO 64×64 для OPL, 128×128 для RiptOPL).
  - Источники по типам: xlenore — COV (плоская обложка, 3-D рендер `covers/3d/` вторым вариантом); libretro — COV (`Named_Boxarts`), SCR (`Named_Snaps`), SCR2 (`Named_Titles`), LGO (`Named_Logos`). Для ICO, COV2, LAB и BG открытого источника нет: их дают наборы картинок (ADR-0033) или ручная замена. `SourceEntry.kinds` сообщает интерфейсу, что есть у источника. *Заменено ADR-0035: у каждого типа теперь есть сетевой источник (копия OPL Manager на archive.org, ScreenScraper с ключом), а порядок источников свой у каждого типа.*
  - Ключ кэша libretro содержит папку (`Named_Snaps/<имя>`), кроме `Named_Boxarts`, чтобы кэш M4 остался действительным. Производные файлы называются `<ТИП>-<Ш>x<В>.png`.
  - Всё растягивается до размера типа, как это делает OPL, кроме LGO: логотип вписывается в рамку на прозрачном фоне (`Fit::Contain`), иначе надпись искажается.
  - `FindArt` — задание: все источники для одного типа одной игры, уже уменьшенные картинки (PNG в base64) для выбора в карточке игры; выбранный вариант записывается обычным планом `SetArt`. Массовая загрузка (`FetchArt.kinds`) берёт первый найденный вариант по порядку источников.
  - Карточка игры показывает восемь слотов с превью, размером и действиями «Скачать», «Заменить» (файл, буфер обмена, перетаскивание) и «Удалить»; каждое действие — план с резервной копией (ADR-0025).
- **Последствия.** В запросах и журналах тип картинки — строка `ArtType`; клиент без поля `kinds` получает только COV. ICO 128×128 на стандартном OPL остаётся вопросом для проверки на консоли (research/13 §6).

## ADR-0033 — Наборы картинок: только игры на носителе, один проход, имена OPL Manager и art.tar
*2026-10-23, принято в M5.* Уточняет SPEC ART-5, ADR-0007 и ADR-0025.
- **Контекст.** У пользователей есть резервные копии картинок OPL Manager (zip около 6 ГБ с archive.org, десятки тысяч игр), папки с картинками и `art.tar` от RiptOPL и wOPL. Частный сервер OPL Manager трогать нельзя (правило 3). Имена в копиях OPL Manager отличаются от имён OPL: скриншоты и фоны пронумерованы (`SCR_00`, `SCR_01`, `BG_00`), расширения смешаны (research/13 §3).
- **Решение.**
  - `ImportArt` — задание: читает выбранные наборы (папки, .zip, .7z, .tar, отдельные картинки) один раз от начала до конца и берёт **только картинки игр на носителе** (решение владельца продукта 2026-10-23); остальные считаются в уведомлении плана. Задание заканчивается планом: ничего не пишется до подтверждения.
  - Имена разбираются точно (`yaoplm_formats::art::pack_picture`), без учёта регистра и где угодно в наборе: `<ID>_<ТИП>.<расширение>` и нумерация OPL Manager (`SCR_00` → SCR, `SCR_01` → SCR2, `BG_00` → BG, остальные номера не используются). Если на один слот есть несколько файлов, выигрывает png, затем bmp, затем jpg, затем остальные.
  - Каждая картинка перекодируется в PNG под размер профиля, как скачанная (ADR-0032), и проходит через кэш `art-cache/local/`. Картинка больше 16 МиБ или нечитаемая пропускается с причиной. Картинки, которые на носителе уже есть, остаются, если пользователь не попросил заменять; заменённые уходят в `.yaoplm/backup/` (ADR-0025).
  - Чтение: zip и 7z через `archive::for_each_file` (solid-блок 7z декодируется один раз), tar — собственным снисходительным читателем ustar (нулевые блоки пропускаются, длинные имена GNU и pax, размеры base-256), он покрыт fuzz-целью. Папка обходится на глубину до 8, скрытые файлы пропускаются, открываются только имена, похожие на картинки. На сервере наборы выбираются внутри разрешённых корней (`PathPolicy`).
  - Интерфейс: «Импортировать картинки» в библиотеке (выбор наборов, типов и «Заменять картинки, которые уже есть на носителе»), журнал задания называет набор и файл каждой картинки.
  - Сбои чтения. В папках и zip каждая картинка читается сама по себе: картинка, которую не открыть или не распаковать (повреждённая запись, неподдерживаемый метод сжатия, шифрование), и папка, которую не прочитать, пропускаются с путём и причиной, а остальной набор берётся. Нерелевантные файлы (тип не выбран, игры нет на носителе, слот занят) даже не открываются. Поток tar и 7z при ошибке декодирования читать дальше нельзя, поэтому такая ошибка, как и набор, который не открыть, или повреждённый центральный каталог zip, завершает задание. CLI: `yaoplm art import <root> <наборы>... [--kind T] [--replace]`.
- **Отвергнуто.** Импорт всего набора: заполнил бы флешку картинками игр, которых на ней нет. Распаковка архива во временную папку: удваивает место и время. Чтение архивов на archive.org через `view_archive.php`, как у OPL PC Tools: архив скачивает сам пользователь. *Пересмотрено ADR-0035 (решение владельца продукта 2026-10-24): копию `OPLM_ART_2024_09` (zip без сжатия) YAOPLM читает по картинке Range-запросами; отказ остаётся в силе для `view_archive.php` и solid-7z.*
- **Последствия.** Запись `art.tar` (для RiptOPL) остаётся за ART-6 в v0.3. Названия из `PS2_LIST.CSV` копий OPL Manager не используются: их даёт встроенная база.
- **Уточнение (2026-10-24, проверка на настоящих копиях).** Оглавления `OPLM_ART_2024_09` и `OPLM_ART_2023_07` с archive.org подтвердили раскладку: все 196 745 имён читаются правильно (research/13 §3). По итогам две поправки: картинки из папки `PS1` набора не берутся (их ID пересекаются с ID игр PS2, а OPL ищет картинки игр PS1 не по ID), и PNG, который уже нужного размера, не глубже 8 бит и без чересстрочности, пишется на носитель как есть — палитровые PNG копий 2024 года сохраняют палитру, вместо того чтобы стать RGB в 2–2,6 раза больше.

## ADR-0034 — Простой режим: что прячется, правило согласованности, задания без шума
*2026-10-24, принято в M5.* Уточняет SPEC UI-4, UI-5, ART-8 и ADR-0030, ADR-0031.
- **Контекст.** Владелец продукта нашёл интерфейс перегруженным: обычному пользователю нужны список игр, «Добавить игры» и картинки, а не сортировки, счётчики, конвертация и журналы заданий. Скан флешки появлялся в заданиях, иногда дважды подряд.
- **Решение.**
  - Настройка `simpleMode`, по умолчанию включена, первым пунктом в настройках. Все экраны читают её через один хук `useSimpleMode()`; переключение мгновенное, без перезагрузки.
  - Что видно в простом режиме — таблица в SPEC §5.11. Всё скрытое доступно в расширенном режиме; в расширенном режиме вторичные действия библиотеки (импорт наборов, проверка дампов, конвертация) собраны в меню «Ещё».
  - Правило согласованности: элемент спрятан на всех экранах или ни на одном. Свойство, видимое на карточке игры (тип диска, формат), можно фильтровать в библиотеке; действие, спрятанное в библиотеке (конвертация, проверка дампов), спрятано и в карточке. Каждое правило — строка таблицы и проверка в `simpleMode.test.tsx`.
  - Скрытые фильтры и сортировка в простом режиме не действуют, но остаются в адресе и возвращаются вместе с расширенным режимом.
  - Планы одинаковы в обоих режимах: это проверка перед записью (правило 1 CLAUDE.md).
  - Задания. Скан библиотеки — внутреннее действие, в обоих режимах его нет ни на странице заданий, ни в плавающей панели: ход виден в самой библиотеке. Запрос библиотеки наблюдается на всех экранах, поэтому смена экрана не перезапускает скан; скан, который никто не ждёт, отменяется и в ядре. В простом режиме страницы заданий нет: ход записи — плавающая панель с «Отменить», итог — уведомление (`sonner`, MIT), ошибка висит до закрытия. Построчные шаги транзакций в журналах — только в расширенном режиме.
  - «Скачать картинки» в простом режиме и «Скачать все картинки» в карточке игры — без выбора: все типы, которые есть у включённых источников, только недостающие, затем план. При добавлении игр поиск тоже берёт все такие типы (`FetchArt.kinds` вместе с `import`); в плане перечисляются только ненайденные обложки, остальные типы считаются в итоге поиска.
  - Связь интерфейса с ядром (не с PS2 и не с сетью) показывается только там, где может пропасть: в браузере. Закрывшийся поток событий — ещё не потеря (прокси закрывают простаивающие соединения; сервер шлёт ping каждые 25 с): через 2 с интерфейс спрашивает ядро запросом `Ping`, и только если ответа нет, показывает плашку. Всё за плашкой, и окна, открытые позже, получает `inert`, пока поток не вернётся; после настоящего обрыва библиотека и носители читаются заново. В десктопе ядро в том же процессе, индикатора нет.
  - Скрытые настройки сохраняют значения и действуют (сверка ID при сканировании, источники картинок); если из-за скрытой настройки действие невозможно, сообщение говорит, где её найти.
  - Переключатели добавления («Названия из базы», «Скачивать картинки», «Проверять дампы») живут только на экране добавления, где они включены по умолчанию и запоминаются; в настройках их нет.
- **Отвергнуто.** Отдельные экраны для простого режима: два интерфейса быстро разойдутся. Прятать предупреждения: они объясняют, почему OPL не покажет игру. Прятать «Пересканировать», «N файлов OPL не видит», «Показывать все тома», «Имена файлов» и DAT Redump: без них пользователь не обновит список после правок в проводнике, не поймёт, куда делась игра, не найдёт карту во встроенном картридере и не получит вердикт проверки (решение владельца 2026-10-24).
- **Последствия.** Каждый новый элемент интерфейса относится к одному из режимов и попадает в таблицу SPEC §5.11. Сценарии e2e по умолчанию открывают расширенный режим (`openLibrary`), обход интерфейса (`walkthrough.spec.ts`) идёт в обоих.

## ADR-0035 — Источник для каждого типа картинок: копия OPL Manager по Range, ScreenScraper по ключу, политика регионов
*2026-10-24, принято в M5.* Уточняет SPEC ART-1, ART-2, ART-4, META-4, §5.4.1 и §7, ADR-0007, ADR-0025; заменяет часть ADR-0032 об источниках и пересматривает отказ в ADR-0033. Исследование — research/14.
- **Контекст.** Владелец продукта поставил цель: у каждого типа картинок OPL (COV, ICO, COV2, LAB, BG, SCR, SCR2, LGO) — рабочий сетевой источник с резервными, картинки находятся примерно в 98 % случаев, источник выбирается молча, а главное — верная игра и верный регион. Сетевые источники до этого: xlenore (COV) и libretro (COV, SCR, SCR2, LGO); у ICO, COV2, LAB и BG не было ни одного. Без ключа все восемь типов есть только в последней резервной копии базы OPL Manager на archive.org (`OPLM_ART_2024_09`, zip64 на 5,5 ГБ без сжатия, ключ — ID игры OPL). ScreenScraper отдаёт все типы с регионом, но только зарегистрированной программе. libretro отдаёт для японской DOA2 европейскую обложку, а около 2 % обложек копии OPL Manager побайтно совпадают с обложкой игры другого региона.
- **Решение.**
  - **Копия OPL Manager** — источник `oplm`, все восемь типов. Центральный каталог (8,6 МБ) читается один раз Range-запросами и хранится рядом с кэшем картинок; затем один Range-запрос на картинку со сверкой CRC-32 и размера по каталогу. Отсутствующую картинку программа не спрашивает (archive.org отвечает на неё 503 через 9 с), «не найдено» индекс даёт офлайн. Нумерация OPL Manager: `SCR_00` → SCR, `SCR_01` → SCR2, `BG_00` → BG, при отсутствии фона — `BG_01`+, затем скриншоты, которых OPL больше нигде не показывает (`SCR_02`+). Один поток, секунда между запросами, повторы при 5xx; если ссылка `download` не отвечает, берутся серверы элемента из его метаданных; после сбоя чтения индекса источник отдыхает десять минут. Файл другого размера или несовпадение CRC — индекс удаляется и читается заново. Зеркало — папка с раскладкой копии (`PS2/<ID>/<ID>_<ТИП>.png`).
  - **ScreenScraper** — источник `screenscraper`, все типы: `box-2D`, `box-2D-back`, `box-2D-side`, `support-2D`, `ss`, `sstitle`, `fanart`, `wheel-hd`/`wheel`. Включён, только если у сборки или окружения есть ключ разработчика (`YAOPLM_SCREENSCRAPER_DEVID`, `_DEVPASSWORD`, `_SOFTNAME`; в релиз — из секретов CI, в репозиторий — никогда); иначе источника нет нигде в интерфейсе: ни в настройках, ни в списке источников «О программе» (правило согласованности ADR-0034). Свой ключ разработчика пользователь в интерфейсе не вводит: это регистрация программы, а не пользователя. Учётная запись пользователя необязательна (настройки или `YAOPLM_SCREENSCRAPER_USER`, `_PASSWORD`). Один `jeuInfos.php` на серийный номер (`serialnum`, система 58), кэш 30 дней, «не найдено» — семь. Коды 401, 430, 431, 403, 423, 426 ставят источник на паузу (десять минут, шесть часов, до конца сеанса). Учётные данные не попадают ни в журнал, ни в кэш.
  - **Порядок по типам** (`sources::order`): COV — xlenore, OPL Manager, libretro, ScreenScraper; ICO, COV2, LAB — OPL Manager, ScreenScraper; BG — OPL Manager, ScreenScraper, скриншот libretro; SCR, SCR2, LGO — libretro, OPL Manager, ScreenScraper. Источник, чьи картинки меньше слота, уходит в конец: для RiptOPL (COV 280×400, ICO 128×128) копия OPL Manager последняя. Пользователь порядок не выбирает; в настройках только включение, зеркало и учётная запись ScreenScraper.
  - **Политика регионов** (`yaoplm_net::region`). Упаковка (COV, COV2, LAB, ICO) — только по совпадению ID или серийного номера, по имени Redump с тегом региона игры или по картинке ScreenScraper с этим регионом; пустой слот лучше угаданного. Картинка упаковки из копии OPL Manager, побайтно совпадающая (CRC и размер) с картинкой игры другой группы регионов (NTSC-U, PAL, NTSC-J/K), в тихой загрузке пропускается с причиной «есть только издание другого региона» (`notices.artOtherMarket`), а в карточке игры предлагается последней. Типы, общие для регионов (SCR, SCR2, BG, LGO), если у своего серийного номера ничего нет, берутся у других изданий той же игры (то же название Redump без тегов, до двух, сначала США): так делает RetroArch с коротким именем.
  - `YAOPLM_OFFLINE=1` запрещает любой хост, кроме этого компьютера; его ставят CI и сервер e2e. Тесты работают на зеркалах и локальном Range-сервере; реальное покрытие меряет тест на реальных данных по спискам файлов источников (research/14 §6).
- **Отвергнуто.** Ссылка на картинку через `view_archive.php` без индекса: каждый отсутствующий тип стоит 9 с и ответ 503. Перезалив копии на GitHub (Luden02): быстрее, но без лицензии — решение владельца, пока не используется. LaunchBox: без условий использования и без серийных номеров, только с разрешения LaunchBox. TheGamesDB: серийные UID ошибочны (DOA2). IGDB, MobyGames, GameTDB, SteamGridDB, IGN, Nostlan, база PSBBN — research/14 §5. Сгенерированные LAB и ICO по шаблону (как в PSBBN): выдуманная картинка вместо найденной; если появятся, то выключенными по умолчанию.
- **Последствия.** Покрытие по 11 571 серийному номеру с именем Redump (research/14 §1): COV 92,4 %, SCR 83,4 %, BG 82,5 %, SCR2 75,9 %, LGO 73,6 %, COV2 56,6 %, ICO 52,7 %, LAB 52,1 %. Цель 98 % без ScreenScraper не достигается: у японских и корейских изданий упаковки 25–32 %, и других открытых источников для неё нет. Первая картинка из копии OPL Manager ждёт оглавление (в живой проверке 37 с), дальше 0,4–1,6 с на картинку (archive.org бывает и медленнее, до 5 с); задание показывает ход и отменяется. Если элемент archive.org пропадёт, источник перестанет отвечать, а кэш останется.

## ADR-0036 — Настройки игры и VMC: правила меню OPL, только изменённое, карты не перезаписываются
*2026-10-24, принято в M5.* Уточняет SPEC CFG-1, CFG-2, CFG-5, VMC-1, §5.11.1, ADR-0019, ADR-0020, ADR-0021 и ADR-0034. Исследование — research/15.
- **Контекст.** Редактор настроек игры должен писать то, что OPL потом прочитает так же, как своё, и не портить чужое: в общих базах CFG описания длиннее 255 байт, старые биты режимов 0.9.3 (`$Compatibility=100`), файлы с LF; соседние менеджеры теряют ключи (OPLNova), пишут `$GSMSource=0`, который OPL считает настройкой «для игры» (OPL PC Tools), и создают карты из нулей, которые OPL отвергает (OrbitPS2). Само меню OPL пересоздаёт карту другого размера без вопроса, а при выходе из окна VMC создаёт карту на 8 МиБ для каждого слота без файла.
- **Решение.**
  - **Правила записи — как у «Сохранить» в меню OPL** (`guiGameSaveConfig()`, research/15 §1.1): значение по умолчанию удаляет ключ; GSM, читы и PADEMU «для игры», пока есть ключ `...Source` (пишется `1`), «глобально» — когда его нет (ключ удаляется, значения для игры остаются в файле, как в OPL); запись любой настройки, кроме слотов VMC, добавляет `$ConfigSource=1` — так обновление списка совместимости OPL не трогает настройки пользователя. `$AltStartup` — заглавными, не длиннее 21 символа и без `;1`: OPL собирает `cdrom0:\<имя>;1` в буфер на 32 байта.
  - **Пишется только изменённое.** Редактор сравнивает настройки с тем, что в файле сейчас, и трогает только отличающиеся; остальные ключи, строки, порядок, BOM и окончания строк остаются побайтно (CFG-1). Значения, которые OPL не понял бы, проверяются только у изменённых настроек: странный `$AltStartup` или длинное имя карты, записанные другой программой, не мешают поменять режим. Биты `$Compatibility`, которые уже есть в файле, сохраняются (старые режимы 7 и 8 из 0.9.3, биты RiptOPL с другой флешки); новые биты должны быть известны профилю (0x01–0x20, у RiptOPL до 0x80). Интерфейс показывает только режимы профиля и о лишних битах говорит.
  - **`$DMA` не показывается в редакторе и не пишется**: он действует только на внутреннем HDD (и на BDM поверх ATA в 1.2, где уровень игнорируется), а HDD у YAOPLM пока нет (HDD-1). Ключ в файле сохраняется и виден в списке ключей; вернуть поле — вместе с HDD.
  - CFG wOPL (libconfig) показываются, но план правки отклоняется с причиной (CFG-1).
  - **План.** Одна транзакция на игру: папка `VMC/` и новые карты, затем копия CFG в `.yaoplm/backup/<id>/` (CFG-5) и атомарная запись CFG; эта запись — точка фиксации, всё до неё откатывается. Транзакция несёт список ключей «было → стало» (`cfgChanges`), план показывает его в обоих режимах. Без изменений план не строится (`settingsUnchanged`).
  - **Карта — как у genvmc OPL побайтно** (research/15 §2.1): суперблок с полями `MCDevInfo`, косвенная FAT в кластере 8, FAT, корневой каталог с `.` и `..`, остальное 0xFF, без ECC, ровно 8, 16, 32 или 64 МиБ; время — по японскому, как часы PS2. Сверено с `pc/genvmc` OPL (всё, кроме времени, побайтно), с mymcplusplus (`check`, `df`, запись сохранения) и с картами genvmc из ps2vmc-tool (суперблок). Время создания хранится в шаге плана, поэтому восстановление после сбоя пишет ту же карту.
  - **Запись карты** — новый шаг `WriteVmc`: временный файл `.yaoplm-part`, место резервируется до первого байта (ADR-0019), синхронизация, переименование. После записи Windows сообщает число кусков файла (`FSCTL_GET_RETRIEVAL_POINTERS`); если их больше одного, итог записи несёт предупреждение `vmcFragmented` (`ExecutionReport.notices`), потому что OPL на BDM такую карту не возьмёт. На Linux и macOS подсчёт появится с проверкой фрагментации всей библиотеки (IMP-7b).
  - **Существующая карта не перезаписывается.** Создать карту с занятым именем можно только явным запросом замены (`replace`, `--replace`, галочка в интерфейсе); старый файл до записи новой переносится в `.yaoplm/backup/<id>/VMC/` вместе с сейвами — удаления нет, откат возвращает его на место (как с картинками в ADR-0025). Удалять и переименовывать карты YAOPLM по-прежнему не умеет (ADR-0020).
  - **Имя по умолчанию — `<ID>_<слот>`**, как в OPL 1.1.0, плюс `generic_0`/`generic_1`. Таблицу групп серий из `src/vmc_groups.c` OPL 1.2 не берём: у файла нет ни заголовка лицензии, ни указания, откуда данные, а код OPL под AFL-3.0 мы не переносим (ADR-0002). Имя группы пользователь может ввести сам.
  - **Простой режим** (решение владельца продукта 2026-10-24): в карточке игры — режимы совместимости 1–6 и карта памяти для слота 1 (выбрать из `VMC/` или создать с именем по умолчанию на 8 МиБ). Слот 2, размер и имя карты, GSM, читы, PADEMU, `$AltStartup`, путь CFG и список ключей — только в расширенном режиме. Настройки — редактор, а не свойство игры, поэтому фильтра в библиотеке для них нет (правило согласованности ADR-0034 касается свойств и действий).
  - CLI: `yaoplm cfg <root> <game>` показывает, с `--mode`, `--no-mode`, `--vmc`, `--alt-startup`, `--set`, `--unset` планирует правку; `yaoplm vmc ls` и `yaoplm vmc create … [--game G --slot 0|1] [--replace]`.
- **Отвергнуто.** Переписывать CFG целиком, как `configWrite()` OPL: теряются комментарии, длинные значения обрезаются до 255 байт. Писать `$...Source=0` для «глобально»: OPL читает это как настройку игры. Удалять старую карту с подтверждением удаления: сейвы пропадут безвозвратно, а перенос в резервную папку стоит только места. Нулевой или «разреженный» файл вместо форматированной карты. Размеры больше 64 МиБ (OPL PC Tools): меню OPL их не создаёт.
- **Последствия.** OPL видит настройки, записанные YAOPLM, как «Пользовательские» (`$ConfigSource=1`). Замена карты оставляет в `.yaoplm/backup/` до 64 МиБ на карту. Подсчёт кусков карты есть пока только на Windows. Профиль RiptOPL пишет 0 режимов удалением ключа, как OPL; явный `$Compatibility=0`, которым RiptOPL выключает свои режимы по умолчанию, и его дополнительные ключи — задача профиля RiptOPL (ART-6, M6).

## ADR-0037 — Проверка фрагментации: счёт от ОС, правило профиля, предупреждение после записи
*2026-10-24, принято в M5.* Уточняет SPEC IMP-7b, LIB-4, §5.11.1, ADR-0019 и ADR-0036. Исследование — research/06 §1.11.
- **Контекст.** OPL на BDM (USB, MX4SIO, iLink, BDM HDD) при запуске игры спрашивает у драйвера куски каждого файла и кладёт их в одну таблицу на 64 записи (`BDM_MAX_FRAGS`). Upstream сверяет лимит с каждой частью отдельно, поэтому игра, которая превышает его только в сумме, не получает внятного отказа. OPL 1.1.0 требует, чтобы каждый файл игры был одним куском, а VMC должна быть одним куском на любой сборке. Ни один соседний менеджер кусков не считает: TinyPS2Manager предупреждает по числу файлов на носителе, остальные молчат.
- **Решение.**
  - **Счёт — у ОС, без чтения FAT с устройства.** Windows — `FSCTL_GET_RETRIEVAL_POINTERS`, без прав администратора. Linux — `FS_IOC_FIEMAP`, а если ФС его не умеет, `FIBMAP` раз на кластер. У драйверов vfat и exfat FIEMAP нет вовсе, а FIBMAP ядро отвечает только процессу с `CAP_SYS_RAWIO`, так что без root на FAT32 и exFAT счёт неизвестен. macOS — `fcntl(F_LOG2PHYS_EXT)`. Соседние экстенты, которые продолжают друг друга на устройстве, — один кусок. Ошибка «не умею» превращается в явное «неизвестно» (`Fragments::Unknown`), а не в «всё хорошо» и не в предупреждение.
  - **`unsafe` — в трёх модулях** вместо одного (уточнение ADR-0019): `sys/windows.rs`, `sys/fiemap.rs` (ioctl через `rustix::ioctl`) и `sys/log2phys.rs` (`fcntl` через крейт `libc`, только на macOS). Структуры ioctl выделяет Rust, у каждого блока комментарий `SAFETY`. `libc` (MIT/Apache-2.0, команда rust-lang) уже был в дереве зависимостей; в `rustix` нет произвольного `fcntl`.
  - **Правило — от профиля** (`LoaderProfile::fragment_limit`): 1.2.0 beta и RiptOPL — не больше 64 кусков на игру в сумме по всем частям, 1.1.0 — каждый файл одним куском. Проверка идёт только на локальных FAT32 и exFAT: SMB, MMCE и NTFS-папки лимита не имеют.
  - **Библиотека** (LIB-4): после сканирования API считает куски каждой игры и VMC из её CFG. Игра сверх лимита получает предупреждение `gameFragmented` или `gameFragmentedOpl110`, карта в слоте — `vmcSlotFragmented`; они видны в карточке игры и попадают в фильтр «Только игры с предупреждениями». Число кусков показывается в сведениях карточки (только в расширенном режиме), в колонке `PIECES` у `yaoplm scan` и в строке `Pieces:` у `yaoplm info`.
  - **После записи** (решение владельца продукта 2026-10-24): исполнитель считает куски игры, которую транзакция импорта или конвертации только что записала, и при превышении кладёт в итог то же предупреждение с советом. В плане до записи предупреждения нет: число кусков известно только после записи, а косвенные признаки (мало места, уже фрагментированные игры) дают ложные тревоги. План помнит профиль, для которого построен (`Plan.profile`, в журнале — `opl-1.2`, `opl-1.1`, `riptopl`), чтобы восстановление проверяло по тому же правилу.
  - **Совет — как в README OPL:** скопировать игры на компьютер, отформатировать носитель и добавить их снова. Дефрагментаторы не советуем (README OPL прямо их не рекомендует), поэтому из текста `vmcFragmented` слово «дефрагментируйте» убрано. YAOPLM сам ничего не дефрагментирует.
- **Отвергнуто.** Свой разбор FAT32/exFAT с блочного устройства: на Linux нужен доступ к `/dev/sdX` (группа `disk` или пароль udisks), на Windows — права администратора, а выигрыш — только Linux без root. Решение владельца продукта 2026-10-24: пока «неизвестно». Предупреждение в плане — см. выше. Дефрагментация средствами YAOPLM.
- **Последствия.** На Linux без root на FAT32 и exFAT вместо числа видно «неизвестно». На macOS 15 тоже: драйверы FAT32 и exFAT в пространстве пользователя `F_LOG2PHYS_EXT` не отвечают (CI `real-fs-macos`, 2026-10-24); код остаётся — если Apple добавит ответ, числа появятся сами. CI `real-fs` проверяет оба случая (без root и под root через `sudo -E`), задача `real-fs-macos` — подключённые образы `hdiutil`. Neutrino (NHDDL, лаунчер Neutrino у RiptOPL) делит те же 64 записи между образом и обеими VMC; это правило появится с профилями этих загрузчиков.

## ADR-0038 — Путь новичка, выбор сборки и версии, замена сборки
*2026-10-24, принято по решению владельца продукта.* Уточняет ADR-0013, ADR-0022 и ADR-0034; детали — SPEC UI-6 (§5.11.2), LDR-6 (§5.10.2), LDR-7 (§5.10.3), находки — research/07 §1.11.
- **Контекст.** Владелец хочет, чтобы программа вела полного новичка: вставил флешку — и ему сказано, что делать дальше, в простом режиме, который включён по умолчанию. В мастере установки нужен осознанный выбор сборки (официальный OPL 1.1.0 и 1.2.0 beta, YAOPL, RiptOPL) с версией, датой, размером и списком изменений, выбор конкретной версии и замена одной сборки другой без потери игр. Репозитории хранят релизы по-разному: upstream перезаписывает `latest` на месте и из выпусков 1.x хранит только `v1.0.0` и `v1.1.0`, YAOPL публикует только вершину `master`, RiptOPL — только пересобираемые варианты.
- **Решение.**
  - Следующий шаг новичка вычисляет ядро по тому, что оно уже знает (`InspectDevice`, сканирование, журналы), без сети: значение перечисления в ответе, тексты — в интерфейсе на каждом языке. Порядок состояний фиксирован (SPEC §5.11.2). Подсказки есть в обоих режимах, в расширенном — одной строкой.
  - Съёмный носитель с вердиктом «Не подходит для OPL», который исправит форматирование (не та ФС или разметка), получает «Подготовить носитель…» — мастер DEV-4 с обязательным форматированием и всеми защитами ADR-0013. Кнопок установки, обновления и замены у него по-прежнему нет (ADR-0022). Носитель, который не исправить (системный, только чтение, сектор не 512 байт), получает только объяснение.
  - Мастер подготовки выбирает ФС сам по способу запуска и сборке (research/06). На «Не знаю» — FAT32: её читают все сборки OPL и все способы запуска, а большие игры уходят в `ul`.
  - Описания сборок и отметка «Рекомендуем» — данные каталога (`summary` на каждом языке интерфейса, `recommended`), а не файлы переводов: каталог обновляется без выпуска программы. Тест каталога проверяет, что языки все.
  - Выбор версии — только из релизов GitHub репозитория сборки, отфильтрованных каталогом по наличию профиля (§4 SPEC): у upstream это `latest` и `v1.1.0`. Прежние беты 1.2.0 на GitHub не хранятся и не выбираются. Архив сборок OPL на MEGA, на который ссылается README, не источник загрузки: нужен свой клиент MEGA, а ADR-0014 требует официальных релизов; такую сборку пользователь ставит из своего архива (LDR-2). RiptOPL выбирается по вариантам (каналы каталога), а не по версиям. CI форка YAOPL будет публиковать каждую сборку неизменяемым релизом с тегом версии рядом с `latest` (задача в репозитории форка). Выбор версии — только в расширенном режиме: новичку нужна последняя сборка канала.
  - Замена сборки — один план: сначала конвертации, потом папки, загрузчик последним. Игры, обложки, CFG, VMC и читы не трогаются, глобальные настройки загрузчиков не переносятся и не удаляются. До подтверждения план проверяет библиотеку по профилю новой сборки и перечисляет, что перестанет работать, с предложением исправить (ZSO → ISO, JPG и BMP → PNG). На OPL 1.1.0 на exFAT обычной заменой не переходим: только объяснение и путь через подготовку носителя заново.
  - Текст релиза — чужие данные: показываем начало простым текстом, не больше 10 пунктов, ссылки только на github.com.
- **Отвергнуто.** Подсказки, которые интерфейс выводит сам без шага от ядра: веб и CLI разошлись бы. Скачивание старых бет OPL с MEGA. Хранение копий старых сборок OPL у нас (ADR-0014: бинарники не распространяем). Выбор версии в простом режиме.
- **Последствия.** В каталоге появляются поля `summary`, `recommended` и правило отбора версий канала; в API — шаг пути новичка у `InspectDevice` и раздел «Что изменится для игр» у плана замены. Нужна задача в репозитории YAOPL: версионные релизы и правка `FORK.md`. RiptOPL в описаниях и замене — вместе с форками в M6. Какую сборку рекомендовать новичку, решает владелец (SPEC, открытый вопрос 7).

## ADR-0039 — Автоопределение профиля: признаки по силе, ключ носителя, «Авто» по умолчанию
*2026-10-24, принято в M5.* Уточняет SPEC LIB-1, §5.1.1, ADR-0004 и ADR-0023. Исследование — research/16 (признаки версий OPL и форков), research/07 §1.9.
- **Контекст.** ADR-0023 решил, что профиль определяется по носителю, а настройка задаёт умолчание и переопределение. Каталога загрузчиков, манифеста установки и истории хешей (LDR-1…LDR-4) ещё нет, ELF упакованы ps2-packer, и у OPL 1.1.0 и 1.2 одинаковое имя `OPNPS2LD.ELF`. Исследование признаков (research/16) показало, что часть правил SPEC §5.1.1 неточна: ключи `mmce_*` пишет и YAOPL; ключи 1.2 в `conf_opl.cfg` переживают откат на 1.1.0, а сильнее их — отсутствие ключей, которые пишет каждая бета со сборки 1871; `games.bin` по размеру записи говорит, какое поколение OPL последним листало папку; одна папка `nhddl/` ещё не NHDDL.
- **Решение.**
  - **Признаки по уровням** (ядро, `yaoplm_core::detect`), решает первый уровень, где признаки согласны:
    1. ELF, чей SHA-256 есть в `data/loader-hashes/opl-stable.txt` (все 34 ELF из официальных архивов v1.0.0 и v1.1.0, посчитаны YAOPLM 2026-10-24: у этих релизов GitHub хешей не отдаёт) — «точно», правила 1.1.0;
    2. файлы одного семейства: `title.cfg` RiptOPL с `Version=`, `settings_riptopl.cfg`, `conf_riptopl.cfg`, `config.path`, `favourites.bin` (`OFAV`), `ART/art_cache.bin` (`ARC\0`); `wopl_*.cfg`, `conf_wopl.cfg`, `conf_uopl.cfg`; `nhddl/cache.bin` (`NIDC`), `nhddl/lastTitle.bin`;
    3. `CD/games.bin`, `DVD/games.bin`: записи по 92 байта — OPL 1.1.0 или бета до сборки 2016, по 188 — бета со сборки 2017 или форк;
    4. `conf_opl.cfg`: ключи, которые 1.2 пишет всегда (`bdm_cache`, `enable_bgm`, `x_sensitivity`, `enable_bdm_hdd` и соседи, `mmce_*`) — 1.2; ключи OPL без них — правила 1.1.0;
    5. имена ELF: `RIPTOPL*`, `WOPNPS2LD*`, `nhddl*`, `OPNPS2LD*`, `OPL.ELF`.
  - exFAT и ZSO исключают 1.1.0 для уровней 3–5, а без других признаков дают 1.2.0 beta. Более сильный признак 1.1.0 на таком носителе остаётся: что носитель OPL 1.1.0 не подходит, говорят советы носителя (DEV-2) и уведомление о невидимых ZSO.
  - Признаки одного уровня, которые спорят (например, два разных загрузчика по именам), ничего не решают: определение идёт ниже, а на карточке — уведомление «несколько загрузчиков». `games.bin` другого поколения, чем выбранный загрузчик, — тоже уведомление: консоль, возможно, запускает другую копию OPL (с карты памяти).
  - Без признаков — OPL 1.2.0 beta («по умолчанию»); обложки JPG тогда добавляют подсказку (беты со сборки 2169 их не загружают), профиль не меняют.
  - wOPL, uOPL, NHDDL, форк с MMCE и YAOPL получают правила 1.2.0 beta, пока у них нет своих профилей.
  - **Что действует** (API, `ActiveProfile`): переопределение для носителя, затем явный профиль в настройках, затем определение. Ответы `ListDevices` и `InspectDevice` несут профиль, источник, причину (фраза ядра), найденные загрузчики и уведомления; советы носителя считаются для действующего профиля.
  - **Ключ переопределения** — `serial:<серийный номер тома>` для USB и SD (флешка сохраняет выбор под другой буквой диска), `path:<корень>` для папок и сетевых папок. Переопределения хранятся в настройках интерфейса (у десктопа и браузера свои, как остальные настройки); на носитель ничего не пишется.
  - **Настройка** (*заменено ADR-0040: настройки больше нет*) «Профиль загрузчика»: «Авто (по носителю)» по умолчанию. Старая сохранённая настройка OPL 1.2.0 beta (она сохранялась при любой правке настроек) становится «Авто», осознанно выбранные OPL 1.1.0 и RiptOPL остаются.
  - **Интерфейс:** строка «Загрузчик: профиль — причина» с меню «Изменить» (профиль для этого носителя или «Авто») на карточке носителя и в шапке библиотеки, в обоих режимах. Сканирование библиотеки ждёт ответа носителя, чтобы не просканировать флешку под 1.1.0 по правилам 1.2.
  - **CLI:** `--profile auto` по умолчанию; `yaoplm device` и `yaoplm scan` пишут профиль и причину, `yaoplm device` — ещё и найденные загрузчики.
- **Отвергнуто.** Хранить переопределение на носителе (`.yaoplm/profile.json`): это запись, которой пользователь не просил (решение владельца продукта 2026-10-24). Признак по одной папке `nhddl/` или `POPS/`: их создают и установщики PSBBN, и менеджеры. Чтение версии из упакованного ELF: строка версии видна только в неупакованных VARIANTS — это задача LDR-4. *Уточнение ADR-0041:* строка версии читается и из упакованного релизного ELF (в нём обычный поток LZMA) и стала уровнем определения.
- **Последствия.** На флешке, с которой OPL не запускается (OPL на карте памяти), профиль почти всегда «по умолчанию», пока консоль не оставит `games.bin`; YAOPLM удаляет `games.bin` после своих записей (IMP-8), так что признак появляется снова только после просмотра на консоли. Признаки — снимок кода на 2026-10-24; YAOPL и форки меняются быстро, перед изменением правил их нужно сверять с текущим кодом (research/16 §13).

## ADR-0040 — Профиль только по носителю: без глобальной настройки; манифест проверяется хешем
*2026-10-25, принято по решению владельца продукта.* Уточняет SPEC LIB-1, §5.1.1, LDR-4, §5.10.1, ADR-0023 и ADR-0039.
- **Контекст.** После ADR-0039 у настройки «Профиль загрузчика» осталось два смысла: «Авто» (по носителю) и явный профиль, который **заглушал** определение на всех носителях. Владелец продукта (2026-10-25): у каждого носителя свой загрузчик, пользователь часто не знает его версию, и глобальный выбор, который сильнее того, что лежит на носителе, только путает; для исключений есть выбор на карточке носителя. Тогда же — о будущем манифесте установки (LDR-3): пользователь может сам заменить OPL, и манифест будет описывать старую сборку.
- **Решение.**
  - **Глобальной настройки профиля нет.** Действует выбор для носителя на его карточке (ключ — серийный номер тома или путь, ADR-0039), иначе определение по файлам носителя (уровни SPEC §5.1.1), иначе OPL 1.2.0 beta.
  - Сохранённые раньше `loaderProfile` и `profile` при чтении настроек игнорируются, переопределения для носителей остаются.
  - API: поле `profile` у `ListDevices` и `InspectDevice` остаётся для CLI (`--profile` задаёт профиль на один запуск); интерфейс его не передаёт. Источник `setting` переименован в `explicit`.
  - **Манифест сам ничего не решает.** При распознавании (LDR-4) YAOPLM считает SHA-256 найденного ELF и сверяет его с манифестом:
    - совпал — сборка точно та, что записана в манифесте;
    - не совпал — ELF заменили без YAOPLM: решают фактические файлы (история хешей, `title.cfg`, имена, признаки §5.1.1), а карточка носителя показывает, что манифест устарел;
    - ELF по пути манифеста нет — то же, манифест устарел.
    Манифест не переписывается сам; его обновит следующая установка или обновление через YAOPLM.
- **Отвергнуто.**
  - Глобальный профиль как запасной на случай «признаков нет»: путает так же, а один выбор на карточке решает это для конкретного носителя навсегда.
  - Перенос старого явного профиля в переопределения: неизвестно, к каким носителям он относился.
  - Манифест как самостоятельный признак выше хеша: он описывает прошлое, а не то, что лежит на носителе.
- **Последствия.**
  - Кто выбрал в настройках OPL 1.1.0 или RiptOPL, после обновления получает профиль по носителю; где признаков нет, профиль выбирается на карточке один раз.
  - На флешке без признаков (OPL стартует с карты памяти, консоль ещё не оставила `games.bin`) профиль — «по умолчанию» с понятной причиной на карточке и в шапке библиотеки, а не скрытая настройка.

## ADR-0041 — Версия внутри ELF загрузчика; вопрос о профиле для подготовленного носителя без признаков
*2026-10-25, принято по решению владельца продукта.* Уточняет SPEC LIB-1, §5.1.1, LDR-4, ADR-0039 и ADR-0040. Исследование — research/16 §1.6, §9–§13.
- **Контекст.** Строку версии считали недоступной: релизные ELF упакованы ps2-packer. Проверка 2026-10-25 показала, что в них обычный поток LZMA: заголовок ps2-packer из шести чисел, байт свойств, словарь, данные и маркер конца за байт до размера из заголовка. Владелец продукта попросил встроить эту версию в определение и согласовать её с остальными признаками, в том числе там, где файлы настроек остались от прежнего форка, установка кривая или признаков нет вовсе. Если признаков нет, пользователь должен сам выбрать версию, а «не знаю» — давать правила 1.1.0. Пустой носитель вопроса не получает: сначала на него ставят загрузчик.
- **Решение.**
  - `yaoplm_formats::ps2_elf` читает строку версии: открытым текстом в неупакованных ELF, после распаковки LZMA — в упакованных. Строка ищется как отдельная C-строка или после `/` (`RiptOPL/v…`, `User-Agent`: в сборках RiptOPL с RetroAchievements другой копии нет). Распаковка ограничена 32 МиБ (вся память EE), ничего не запускается; повреждённый или обрезанный файл даёт «версия неизвестна», а не ошибку и не чужую версию.
  - Уровни определения (SPEC §5.1.1):
    1. контрольная сумма и версия внутри ELF вместе — «точно»; два ELF, которые на этом уровне спорят (OPL 1.1.0 в `UPDT/` и бета в `APPS/`), ничего не решают;
    2. файлы одного семейства;
    3. `games.bin`;
    4. `conf_opl.cfg`;
    5. имена ELF.
  - Версия даёт правила: 1.0, 1.1 и беты upstream до сборки 1871 — правила 1.1.0; суффикс форка (`-yaopl`) отменяет лестницу номеров.
  - Семейство ELF берётся из строк самой программы (`settings_riptopl.cfg`, `conf_riptopl.cfg` — RiptOPL; `wopl_settings.cfg`, `conf_wopl.cfg` — wOPL; `conf_uopl.cfg` — uOPL; `conf_opl.cfg` — OPL), а не из имени файла, поэтому переименованный ELF узнаётся. `title.cfg` RiptOPL уступает версии внутри ELF.
  - Новые уведомления: файлы другого загрузчика рядом с тем, чей ELF решил (`leftoverLoaderFiles`, «вероятно, остатки прежней установки»); файл с именем загрузчика, который не программа PS2 (`loaderNotPs2Elf`).
  - OPL 0.5–0.9.3 упакованы не LZMA: их 25 ELF дописаны в `data/loader-hashes/opl-stable.txt` и узнаются по контрольной сумме с правилами 1.1.0.
  - Ответ `InspectDevice` и `ListDevices` несёт `detected.library`: в корне есть папки OPL (кроме одной `APPS/`) или `ul.cfg`.
  - **Вопрос «Какой OPL вы запускаете с этим носителем?»** — строка на карточке носителя и в библиотеке, не окно. Он показывается, только если профиль взят по умолчанию (признаков нет), `library` истинно и доктор носителя (DEV-2) не считает носитель непригодным для OPL: на системном диске, NTFS-флешке и подобных вопрос о версии ничего не значит. Ответы — OPL 1.2 или YAOPL, OPL 1.1.0, RiptOPL, «Не знаю (правила для любого OPL)» — сохраняются как выбор для носителя. «Не знаю» хранится как `unknown` и отправляется ядру как правила OPL 1.1.0; строка загрузчика объясняет это. Если позже файлы носителя говорят другое, чем выбор, показывается «По файлам носителя это …» с кнопкой «Вернуть «Авто»».
- **Отвергнуто.**
  - Окно при подключении носителя: флешка без признаков — обычный случай (OPL на карте памяти), окно на каждое подключение мешает.
  - Вопрос для пустого или чужого носителя: ему нужна установка загрузчика (путь новичка, SPEC §5.11.2), она и решает профиль.
  - Кнопка «Позже», которая молча оставляет правила 1.2.
  - Распаковка UCL для OPL 0.x вместо таблицы хешей: сборки заморожены, хешей хватает.
- **Последствия.**
  - Проверка на реальных сборках (research/16 §1.6, §13; `scripts/loader-corpus.py`, тесты `loader_elfs` и `loader_corpus` с `--ignored`): 451 ELF из 98 релизных ассетов дают ровно ту версию, что следует из имён релизов и истории git; 1 649 повреждённых копий ни разу не дали чужую версию; 1 207 сочетаний установок на 303 загрузчиках определяются верно.
  - Каждое определение читает ELF загрузчика целиком (до 64 МиБ) и распаковывает его, порядка 4 МБ на носитель. Fuzz-цель `ps2_elf` добавлена в еженедельный прогон.
  - Признаки — снимок кода сборок на 2026-10-25: перед правкой правил их нужно сверять с текущим кодом (research/16 §13).

## ADR-0042 — Установщик загрузчиков: каталог как данные без истории хешей, пресеты, языки, стартовые настройки и чужой ELF
*2026-10-25, принято по решениям владельца продукта (ответы на вопросы перед LDR-1…LDR-7 в M5).* Уточняет ADR-0014, ADR-0022, ADR-0038 и ADR-0041; находки — research/17.
- **Контекст.** Перед реализацией установщика (SPEC LDR-1…LDR-7, BOOT-1) нужно было решить, куда класть ELF по умолчанию, что делать на MX4SIO, ставить ли языковые пакеты и стартовые настройки и как поступать с чужим ELF на месте установки. Соседние инструменты (research/17) перезаписывают ELF без резервной копии, не пишут манифест и не определяют версию; установщик FreeMcBoot кладёт на карту OPL 1.0.0, а все пять стандартных `FREEMCB.CNF` (1.953, 1.963–1.966) первым пробуют `mass:/UPDT/OPL.ELF`. ADR-0022 предполагал вести историю хешей каждой сборки плавающих каналов; с ADR-0041 версия читается из самого ELF, и владелец продукта спросил, нужна ли тогда история вообще.
- **Решение.**
  - **Каталог.** `data/loaders/index.toml` (порядок сборок и `schema`) и по файлу на сборку: `opl-stable` (тег `v1.1.0`), `opl-beta` (`latest`), `yaopl` (`latest`). Разбор строгий: неизвестное поле — ошибка, новое поле повышает `schema`; программа, которая не знает схему свежего каталога, остаётся на своей копии. Копия вшита в программу (`yaoplm_core::loaders`), свежая из `main` проходит те же проверки. Тесты проверяют, что тексты `summary` и `limits` есть на каждом языке интерфейса (`web/src/locales/*`) и следуют типографике `docs/I18N.md`.
  - **Истории хешей новых сборок нет** (решение владельца продукта 2026-10-25). Сборку на носителе узнаёт строка версии внутри ELF (ADR-0041): на релизах она совпала с именами релизов и историей git у 451 ELF, у трёх скачанных для каталога (1.1.0, бета `latest`, YAOPL) — тоже. Канал каталога по версии задают `fingerprints.versions` и `fingerprints.suffix`: `v1.1.0` — `opl-stable`, `v1.2.0-Beta-…` без суффикса — `opl-beta`, `…-yaopl` — `yaopl`. Таблица `data/loader-hashes/opl-stable.txt` (ADR-0041) остаётся только для замороженных выпусков, у которых версию не прочитать (0.5–0.9.3), и для 1.0.0 и 1.1.0; новых строк в неё не добавляется. Хеш нужен ещё в двух местах: проверить загруженный файл и подтвердить нашу установку (манифест, ADR-0040).
  - **Подтверждение загрузки.** У каждого канала свои источники хешей: `digest` GitHub, файл `SHA256SUMS` релиза, закреплённые в каталоге хеши. Хеш, который пользователь видел до подтверждения, закрепляется в плане и сверяется после загрузки; файл принимается, только если все источники, которые его знают, согласны. У 1.1.0 GitHub хешей не отдаёт, поэтому архивы `OPNPS2LD-v1.1.0.7z` и `OPNPS2LD-LANGUAGES-AND-FONTS-v1.1.0.7z` закреплены в каталоге хешами, посчитанными YAOPLM 2026-10-25; релиз заморожен, и они не меняются.
  - **«Новее».** Внутри одного канала — по номеру сборки из строки версии; номер свежей сборки канала берётся из релиза (имя ассета, имя релиза, тег) при «Проверить обновления» и кэшируется. Дата — `updated_at` ассета, коммит — ссылка тега, а не `published_at` и `target_commitish`. Тот же номер с другим коммитом — другая сборка, а не обновление: номера разных форков не сравниваются.
  - **«Рекомендуем»** — OPL 1.2.0 beta (SPEC, открытый вопрос 7 закрыт).
  - **Пресеты.** На флешке по умолчанию — FreeMcBoot: `UPDT/OPL.ELF`. PS2BBL: `APPS/OPNPS2LD.ELF`. Приложение OPL: `APPS/OPL/OPNPS2LD.ELF` с `title.cfg` (`title=Open PS2 Loader`), у YAOPL — `APPS/YAOPL/` (`title=YAOPL`). Ответ «Не знаю» на вопрос о способе запуска ставит ELF в оба стандартных пути (`UPDT/OPL.ELF` и `APPS/OPNPS2LD.ELF`). Отдельный пресет FMCB 1.953 `OPL.ELF` не нужен: `UPDT/` есть и в 1.953.
  - **MX4SIO.** Мастер спрашивает, где будет работать носитель: флешка USB или SD-карта в MX4SIO; умолчание — по шине (через USB-кардридер SD выглядит как USB). FreeMcBoot с MX4SIO не запускает, стандартного пути нет ни у одного лаунчера, поэтому для MX4SIO — пресет приложения или свой путь, строки BOOT-1 для PS2BBL-MX4SIO (`massX:/…`) и OSDMenu (`mx4sio:/…`), и вариант «OPL на карте памяти» (только папки, без ELF). `APPS/OPNPS2LD.ELF` для MX4SIO — только после проверки на консоли: PS2BBL найдёт его там лишь при определённом порядке устройств.
  - **Чужой ELF на месте установки.** OPL, который YAOPLM узнаёт (манифест, версия внутри ELF или «OPL, версия неизвестна» по имени), заменяется, прежний файл уходит в `.yaoplm/backup/loader/` тем же планом; план показывает размер и SHA-256 заменяемого файла. Файл другого семейства или нераспознанный — только с отметкой «Заменить этот файл» в плане, резервная копия делается и тогда. Удаления нет.
  - **Резервные копии** — три последние на каждый путь; более старые удаляет тот же план, и они видны в нём.
  - **Языковые пакеты** — по желанию, выключены по умолчанию: «Язык меню OPL» с выбором языка. Ставятся только выбранный язык и его шрифт, плоско в `LNG/`; файлы ищутся по именам `lang_<Язык>.lng` и `font_<Язык>.ttf|otf` на любой глубине архива и в одном вложенном zip (у бет — zip внутри 7z, у 1.1.0 — папки). Манифест помнит пакет, «Обновить» обновляет его вместе с ELF: файл языка привязан к версии.
  - **Стартовые настройки** — только в расширенном режиме, по галочке. OPL читает `conf_opl.cfg` с носителя, только если на карте памяти его нет, и тогда сам включает USB в режиме «авто» и дальше сохраняет настройки на носитель (`src/opl.c`, `checkLoadConfigBDM` и `trySaveAlternateDevice`, в `b3a2199` и `v1.1.0`). Поэтому: файла нет — пишем `usb_mode=2` (и `language_text`, если выбран язык); файл есть — меняем только эти ключи, остальные и их порядок сохраняются; предупреждаем, что при настройках на карте файл не сработает. Для MX4SIO не пишем: OPL не увидит файл, пока MX4SIO не включён.
  - **`LICENSE` и `CREDITS`** на носитель не копируются (у бет и YAOPL они есть только внутри 7z); лицензия, авторы и ссылки показываются в окне установки.
  - Варианты сборок (`PADEMU`, `IGS`, `RTL`, `-nosio2man`) в v0.2 не предлагаются. Свежий каталог берётся из `main` (raw.githubusercontent.com) по «Проверить обновления»; ежедневная проверка выключена по умолчанию.
- **Отвергнуто.**
  - История хешей каждой сборки плавающих каналов (ежедневный workflow дописывал бы `digest` и `SHA256SUMS` в `data/loader-hashes/`, а CI форка — `HASHES.txt`): версия внутри ELF узнаёт любую сборку, в том числе беты из архива MEGA и пересобираемые по нескольку раз в день варианты RiptOPL, а история росла бы каждый день, устаревала во вшитой копии и всё равно пропускала бы сборки, заменённые за сутки.
  - Перезапись без резервной копии и «обновление, когда хеш другой» (так делают соседи, research/17 §9 e, g). Копирование `LICENSE` и `CREDITS` на носитель. Стартовые настройки по умолчанию и для MX4SIO. Пресет FMCB 1.953 в корне.
- **Последствия.**
  - У ядра появляется модуль `loaders` (каталог, строки версий и их порядок, канал по версии), у API — `LoaderCatalog`, у CLI — `yaoplm loader ls`.
  - Отличить «файл официального релиза байт в байт» от «собран из того же коммита» нельзя; на профиль и на предложение обновиться это не влияет.
  - Если upstream сменит упаковщик, новые сборки будут «версия неизвестна», пока не обновится чтение ELF (ADR-0041); тесты на корпусе релизов (`loader_elfs`) покажут это на первом же новом релизе.
  - До первой «Проверить обновления» программа без сети не знает о сборках новее тех, что были, когда она вышла; окно «Доступно обновление» работает по кэшу после первой проверки.
  - Задача `HASHES.txt` в CI форка YAOPL снимается; версионные релизы YAOPL (ADR-0038) по-прежнему нужны для выбора версии и отката без резервной копии.

## ADR-0043 — Загрузка сборок загрузчика: задания, проверка по хешу и версии, хранилище ELF, каталог из `main`
*2026-10-25, принято в M5 (LDR-2).* Уточняет ADR-0014, ADR-0022 и ADR-0042.
- **Контекст.** LDR-2 требует скачивать сборки только с официальных релизов и только по действию пользователя, держать загрузку на SHA-256, показывать лицензию и начало списка изменений до загрузки, уметь ставить из своего файла без сети и подтягивать свежий каталог из `main`. Ядро синхронное (ADR-0003), сеть живёт в `yaoplm-net`.
- **Решение.**
  - **Задания.** Сеть — только в заданиях, которые запускает пользователь: `LoaderRelease` (что будет скачано: версия, дата, файл, размер, SHA-256 и чем он подтверждён, лицензия, ссылки на релиз и коммит, до десяти пунктов списка изменений), `DownloadLoader` и `UpdateLoaderCatalog`. `ImportLoader` читает файл пользователя без сети, `LoaderFiles` перечисляет то, что хранится.
  - **Откуда.** Описание релиза — `GET /repos/<repo>/releases/tags/<tag>` с `ETag` прошлого ответа (ответ 304 не тратит лимит GitHub в 60 запросов в час); файлы — только с `https://github.com/<repo>/releases/download/`, ссылка на другой хост или чужой репозиторий в описании релиза отвергается; каталог — `raw.githubusercontent.com/belomaxorka/yaoplm/main/data/loaders/`. Папка-зеркало с той же раскладкой заменяет сеть в тестах, CI (`YAOPLM_OFFLINE=1`) и без интернета.
  - **Загрузка держится того, что видел пользователь.** Запрос `DownloadLoader` несёт SHA-256 из `LoaderRelease`: если плавающий тег успели пересобрать, загрузка отвергается («пересобрали, посмотрите новую сборку»). Скачанный файл проверяется по размеру из релиза, по SHA-256 (все источники, которые его знают, согласны) и затем по версии внутри ELF (ADR-0041): она должна совпасть с версией релиза, если читается. Файл, не прошедший проверку, не сохраняется.
  - **Хранилище.** `<данные>/loaders/elf/<sha256>.elf` и рядом `.json`: версия, сборка, тег, файл релиза и член архива, SHA-256 файла релиза, источник, подтверждён ли хеш, время. Тот же файл релиза второй раз не скачивается. Описания релизов с `ETag` — в `loaders/releases/`, каталог из `main` — в `loaders/catalog/`. Записи пишутся во временный файл с `fsync` и переименованием.
  - **Без сети** «Сведения о релизе» показывают последний сохранённый ответ с пометкой; загрузке нужна сеть.
  - **Свой файл.** ELF или zip/7z ровно с одним ELF загрузчика (по `fingerprints.elf` каталога; в архиве с несколькими — просьба распаковать нужный). Семейство — по строкам программы, версия — изнутри ELF, канал — по каталогу. «Подтверждён» только тот файл, чей SHA-256 есть в таблице замороженных выпусков (`opl-stable.txt`); остальные показываются как «ваш файл, за него никто не ручается».
  - **Каталог из `main`** сохраняется, только если он читается тем же разбором и проверками, что и вшитый, и его схема знакома программе; иначе остаётся прежний. Сохранённый каталог действует только для той версии программы, которая его прочитала: новая программа несёт вшитую копию не старше.
  - **Список изменений** — простой текст: HTML убирается, ссылки остаются только на github.com (коммит или PR раньше профиля автора), служебные строки (контрольные суммы, «Automatic … build», «Full Changelog») отбрасываются, не больше десяти пунктов по 200 символов.
- **Отвергнуто.** Загрузка языкового пакета вместе со сборкой: он нужен только при установке с выбранным языком (LDR-3). Токен GitHub для лимита запросов: хватает `ETag` и кэша. Переход по ссылкам из описания релиза на любой хост: подменённое описание не должно уводить загрузку.
- **Последствия.** У ядра — `loaders::{release, notes, download, local}`, у сети — `yaoplm_net::loaders` (`ReleaseSource`, `LoaderNet`, `LoaderStore`), у API — запросы и задания выше, у CLI — `yaoplm loader release|download|import|files|update-catalog`. Хранилище ELF не чистится само: сборка весит около 1,4 МБ; очистка появится вместе с резервными копиями установки, если понадобится.
